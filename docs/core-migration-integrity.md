# A0 迁移完整性修复与旧六版库基线化

状态：开发修复及独立 PostgreSQL 验证；不是负责人验收结论。范围为 V-MIG-01–03；V-MIG-04 的严格版本策略保持。原始需求文件和既有 001–006 SQL 未改，演示数据库/服务未操作。

## 原文保证与实际机制

原文 A0 要求迁移可重复执行、数据库 schema 落后于程序时拒绝启动。旧实现把排序位置当编号、文件数当目标版本、只看数据库最大编号；这些值相等不能证明历史完整或 SQL 未变。

当前实现见 [migrations.ts](../apps/server/src/core/migrations.ts)：

- 文件名为 `正整数_名称.sql`，按显式数值编号排序；拒绝零、越界、非法名称、重复编号。目标版本为最大明确编号，编号允许留空，绝不按数组位置重新分配。
- 读取每份 SQL 的原始字节，计算 SHA-256；同一内存快照里的字节用于执行和落账。历史格式、注释或换行变动也会改变 checksum。
- 迁移前逐条比较完整账本的编号、名称、checksum。已执行记录必须恰好组成当前清单的完整前缀，才能追加后缀。缺中间记录、历史插入/删除/改名/重新编号、内容修改、未知较高编号均拒绝，拒绝前不执行待迁移 SQL。
- 迁移获取 PostgreSQL 事务级 advisory lock `913456`；所有本批 SQL、版本记录、ledger 初始化同事务提交，失败整体回滚。
- 启动取同一迁移锁后逐条校验，要求完整清单全等，再注册应用并监听。落后和更高数据库都拒启；严格策略没有放宽。
- 普通 `npm run db:migrate` 不会给没有 checksum 的旧账本自动回填。运行中 `/api/health` 仍是启动时已核验版本的报告，不是持续的物理 schema 巡检。

校验依赖可信程序/迁移发布物和可信数据库账本。它能发现文件与已存 checksum 不一致，不能防御能够同时篡改程序、SQL 和数据库账本的管理员；也不会在每次启动穷举真实表结构。迁移仍须使用可在 PostgreSQL 事务内执行的 SQL，不能在迁移正文中自行提交事务。

## 已部署六版库的兼容路径

旧账本没有原始 SQL checksum，无法事后证明当时执行的字节。直接用现有文件生成 checksum 并宣称“历史已经验证”不成立。本轮提供受限的**显式 schema 基线化**，从核验通过时开始保护后续历史一致性。

[legacy-migration-baseline.ts](../apps/server/src/core/legacy-migration-baseline.ts) 内固定了发布 `fa1baa7d7524bf16f379c9c2837fa8cc9ef0bcac` 的六项编号、名称和 SHA-256，不从待核目录现场生成可信清单。该入口只支持完整的旧 001–006 账本，不给任意较旧/较新库通用背书。

执行步骤：

1. 由操作者确认停旧服务，并保证本次核验期间没有其他非协作 DDL 会话。若后续将应用 007，先让旧版中仍运行的序列自然完成，再停旧服务；基线命令不会改序列状态。
2. 显式指定目标 `DATABASE_URL`，执行：

   ```sh
   npx tsx scripts/baseline-legacy.ts --source=git:fa1baa7d7524bf16f379c9c2837fa8cc9ef0bcac
   ```

3. 入口验证本地 001–006 与固定发布清单完全匹配；在同一 PostgreSQL 服务上创建 UUID 独立参考库（`template0`），重放可信六次 SQL。该步骤需要 `CREATEDB` 权限，不会在目标执行这六次 SQL。
4. 目标事务内获取迁移锁，并对参考库列出的所有业务表和 ledger 取 `ACCESS EXCLUSIVE` 锁；5 秒锁超时会回滚。逐条核对旧 ledger，再比较规范化目录定义。
5. 通过后在同一目标事务增加 checksum 及来源字段，保留原 `applied_at`，记录 `checksum_origin=legacy_schema_baseline`、固定发布来源、数据库核验时间和结构摘要。输出 JSON 留存本次证据。参考库/连接在成功和已捕获失败路径清理，清理失败会明确报错。**若目标已提交、后续参考库清理失败，错误和CLI JSON会明确 `targetCommitted=true`，附既有基线证据及参考库UUID；清理失败不代表目标回滚，不可自动再次基线化。** 进程被强杀或提交时连接中断仍需检查实际状态，不能仅据命令非零推断无提交。
6. 基线化仅处理旧六版账本，不执行 007。随后另行执行 `npm run db:migrate`；任何新迁移的前置检查仍然生效，启动仍要求完整当前清单。

规范化比较涵盖 public 的关系、列/默认值/空值/类型/排序规则引用、约束、索引及有效状态、序列定义和归属、触发器（含内部外键触发器的 enabled 等稳定状态）、函数/过程、类型、规则、行级策略，以及安装扩展清单。生成的内部对象 OID/内部触发器名称不参与跨库比较。比较不覆盖业务行数据、当前序列值、角色/所有权、ACL、tablespace、其他 schema 的完整内容或全部 PostgreSQL 配置；这些不被本次基线背书。

迁移锁约束使用本执行器的协作迁移；已知表锁阻止这些表的数据/DDL 写入。它不是全数据库 DDL 防火墙，不能阻止不遵守锁协议的另一个管理连接在核验期间创建函数、类型或新表。因此停写、无其他 DDL 是本入口的明确操作前提，不能把有限锁测试解释成任意并发 DDL 安全。

物理结构一致只证明**本次观察的结构与可信发布结构一致**，不证明历史 SQL 原始字节、过去的副作用或现有业务数据正确。新库和本次以后真正执行的迁移标为 `checksum_origin=executed`，旧六次保持 `legacy_schema_baseline`，两者不会混写。

## 验证及证据边界

专项测试：[migration-integrity.test.ts](../tests/integration/migration-integrity.test.ts)。执行日志：[core-migration-integrity-tests.log](evidence/core-migration-integrity-tests.log)。环境与结果摘要：[core-migration-integrity-verification.json](evidence/core-migration-integrity-verification.json)。

独立 Docker PostgreSQL 17，随机映射端口 `62212`，无宿主数据卷；每项用 `kapibala_test_<UUID>` 数据库；参考库另有 UUID；应用监听随机端口。没有使用演示库、服务端口或模拟器状态文件。

| 对应补验 | 实验及有限结论 |
|---|---|
| V-MIG-01 | 同一个文件/编号/数量，将建表列由 integer 改为 text：旧库的迁移和检查都因 checksum 拒绝，原结构/业务数据/账本不变；独立新库执行修改后的文件得到 text。另验证显式编号 1、2、10 的目标版本是 10。 |
| V-MIG-02 | 保留最大值但删中间记录、历史改名/删除/插入/重新编号、未知更高记录，均在启动校验和迁移入口拒绝且目标不变。非法文件名、零/越界编号、重复编号也拒绝。 |
| V-MIG-03 原子性 | 在第3次记录 INSERT 的 BEFORE trigger 注入异常，此时第2次 SQL/记录和第3次 DDL/数据均已执行；比较证明整批回滚。解除故障后重跑成功，再跑结构、记录、业务值不变。 |
| V-MIG-03 并发 | 两个独立 Node 迁移进程；第一进程持有 `913456` 并在独立测试锁上等待，第二进程被 PostgreSQL 真实报告等待 `913456`。释放测试锁后只加一次业务值，只新增一条版本记录。不是用 Promise 完成顺序推断串行。 |
| A0 启动 | 实际当前清单少最后一份的库，生产 `main.ts` 子进程退出1、未打印监听、随机端口健康请求失败；迁移后真实随机端口健康响应正确。对已完整库篡改 ledger checksum，应用创建也拒绝。 |
| 旧六版 | 真实重放旧001–006并保留旧ledger形状。默认迁移/启动拒绝且无checksum列、无结构/记录/业务变化；显式基线通过，保留业务/原迁移时间并写有限来源。再次基线化拒绝，不刷新证据时间。 |
| 基线拒绝 | 中间记录缺失、名称错配、缺索引、默认值改变、额外函数、内部FK触发器禁用、序列定义改变、发布文件字节变化，均拒绝且无目标变化。锁竞争超时、缺CREATEDB权限亦无目标变化；参考库清理已查。 |
