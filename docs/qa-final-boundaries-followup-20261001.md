## 时间条款核对

原 A5.2 规定从 run 创建起累计在线时间上限为 60 秒、含审计、停机不计；公开终态定义规定 `wall_clock → failed`。QA 本轮静态复核确认，原文没有“必须恰好跑满 60 秒”的明文下限，旧用例将所有小于 60 秒的 `wall_clock` 一律判为提前耗尽，是额外限制。后续用例纠正由 QA 独立维护；此核对不修改旧运行，也不推翻已经证明的真实超限。

“上限”解释不允许伪造耗尽或随意提前结束。若改成剩余预算不足以容纳下一完整阶段时停止，须明确阶段准入、结束原因、未完成工作及现有客户端兼容。当前已批准的计量加强不等于这项新策略自动获准。数据库提交和事件循环调度也没有已证明的最坏耗时界，不能通过固定预留少量毫秒宣称任意负载都满足物理上限。

发送工具的条款不同：已确认 accepted/sent 或明确失败可提前返回；持续未决时原文规定 5 秒后返回 SEND_TIMEOUT。不能把对 60 秒下限的修正直接应用于 5 秒未决等待，不能钳制真实计量或修改开始时刻让测试通过。

## 列表提醒的适用前提

[提醒实施](page-update-notification-implementation.md)及[目录方案](group-directory-profile-proposal.md)要求多页相关变化后保留旧列表、标记过期并禁用旧续页；成功整体刷新、呈现新版本后才能确认提醒。确认本身不能清除过期或恢复旧游标。[前次开发核对](qa-ui-evidence-followup-20261001.md)已经说明“仍显示旧列表且 stale，却独立确认新版本”的组合没有合法入口。

本轮双方静态核对还确认，旧 UI-032 创建 23 条并加载两页后已取完集合，本来就没有下一页。后续有效场景须先保证第二页仍返回续页游标，再验证过期保护、失败刷新保留旧结果、成功刷新替换第一页、现有范围摘要确认以及按新首页响应继续分页。新旧游标字符串不必不同；检查的是客户端所用游标来自哪次成功查询及对应的目录状态，不能把活数据 keyset 误写成服务端撤销旧游标的快照协议。

本轮没有新增“无条件清提示”按钮，也不要求负责人重新选择已批准的确认规则。具体用例重组、自检及新执行由 QA 记录，静态核对不是通过证据。

## 实际交付与仍未关闭的边界

### 投递等待的确定修复

[严格时限专项记录](strict-deadline-followup-20261001.md)保留修前、修后、原始失败和固定源码。工具等待使用原截止时间，在查询前后检查期限，不再把迟到结果用于本次返回，也不在超期后继续读取账号；期限内已确认 `sent` 时，直接返回事实，避免无关账号查询拖住结果。所有权异常仍原样返回，不伪造超时或完成步骤。新定向测试 7 项及关联测试已经由工作线执行。

本次没有为数据库在途查询增加取消能力，也没有改变累计活动预算。局部修复后，普通运行真实活动区间 `[60002,60014]ms`、容量拒绝路径 `[60003,60078]ms` 仍超过 60000ms；四类强制数据库等待仍约 5108–5121ms。它们继续属于严格时限未满足，不能使用“没有重复副作用”或“开发回归通过”替代时间断言。

### 新实验的跨进程计时证据

观察协议新增实际应用进程的单调时钟读数、最后成功采样以及快照来源；控制器将存活桥接读取与进程退出后保留的历史缓存明确区分。汇总工具按父进程请求/响应区间校准不同进程时钟，关联真实强杀与退出、恢复接管和终止区间。它不假定不同进程 `performance.now()` 原点相同或网络往返对称。

完整性检查要求从真实创建/接管起连续观察；晚订阅重建、所有权中断、恢复暂停及缓存时钟均不能充当完整区间。这里检查的是所覆盖 epoch 的连续性，启动到接管之间尚缺整段 `inactive` 见证，不能因求和时未纳入就默认按原文扣除。已观察段下界超过上限能证明失败，反向不能据此证明整个 run 通过。最后确认采样到退出的尾段只是有上下界的不确定区间；成功写库后通知尚未送达也可能发生，因此其零下界不表示实际没有丢计量。单进程恢复帧的 `includesUnsavedTail=false` 保持原意，不被改成全程完整。

该能力仅支持记录中明确的同机、稳定速率单调时钟、连续单所有权、真实无远端在途的持久安全点实验。它不提供任意停电/多实例精确计量保证，旧 QA 缺失帧也不会因此被补造。[接入说明、完整原始帧及最终强杀证据](qa-cross-epoch-evidence-20261001.md)另行固定版本，由 QA 决定能否补足 INT-ACT-001。

### 后续需要取舍的唯一新增方向

当前没有理由让负责人重复确认 D039、文案范围或列表提醒规则。若要继续改变时间控制策略，可评审“剩余预算不足下一阶段已有配置上限时不再启动该阶段”：它可能较早结束运行，并需明确终止原因与未完成工作的语义，仍不能给未知数据库锁等待提供硬上界。本批没有自动实施该策略，没有增加容差或篡改计量。严格物理上限及上述行为调整应分开判断；在取得新有效证据或明确决策之前保留未关闭。

两个独立控制器的启动命令仍为：

```sh
# 各进程使用自己的 registry 与随机回环端口，不复用日常演示资源。
QA_CAPACITY_REGISTRY_DIR='<owned capacity registry>' QA_CAPACITY_PORT='<capacity port>' \
  node --import tsx scripts/qa-capacity-controller.ts
QA_RUNTIME_REGISTRY_DIR='<owned runtime registry>' QA_RUNTIME_PORT='<runtime port>' \
  node --import tsx scripts/qa-runtime-observation-controller.ts
```

两流绑定同一 SUT 的 `target={apiUrl,revision,pid}`：`revision` 为完整候选 SHA，`pid` 是注册中实际 guardian PID；计时和强杀使用另行验证的 `applicationPid`，不能混淆。

| 证据流 | 请求及关联 | 用途 |
|---|---|---|
| capacity | `qa-capacity-control/1`，`hold-admission-capacity`，`{groupId,runId,toolUseId}` | 证明真正容量拒绝、无回调/外部派发以及后续 ready |

| 运行生命周期 | `qa-runtime-observation/1`，`observe-agent-lifecycle`，`{kind:"tool-wait",groupId,runId,toolUseId:"all-run-steps"}` | 实际终止决定、同 attempt 的真实 COMMIT 以及新派发顺序 |
