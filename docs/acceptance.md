## 每一组怎样协作

1. **先说明规则。** 用业务语言说明什么必须成立、什么不允许发生，再对应原文，不先读代码或报测试总数。
2. **先披露实际机制和前提。** 说明比较/去重对象、标识来源、持久化与外部调用顺序、事务/锁范围、失败后的判定依据。区分代码约束、外部协议和操作约定；例如当前迁移比较显式编号、文件名和 SHA-256 的完整历史，不能只说“版本一致”。
3. **再审用例和关键反例。** 预期从原文独立导出，确认故障位置和断言能排除错误实现。后端按业务规则、持久状态、事务/外部边界与恢复说明；前端核对合并、异步竞争、身份隔离及呈现。已执行的第二轮实验使用独立环境，具体结果查证据卡，不使用演示数据故障注入。
4. **最后核对执行证据。** 列出触发条件、断言、实际结果、版本、原始记录和未测边界。证据充分时不为展示重复全套实验；证据缺失时明确补验，不以源码或测试定义代替执行结果。
5. **作有限结论。** 记录通过的具体条款和场景，未覆盖或有偏差的条款保持打开。实现通过、自测通过、负责人评审通过是不同字段。

验收负责人审查风险、证明范围和处理建议，工程侧负责场景构造、验证执行及缺陷定位。独立审查用于补充视角，不替代可复核的执行证据。

**实验停止条件：** 源码与运行版本无法对应、隔离目标不明、出现未授权写入或重复外部效果、操作结果未知时，停止该场景后续写操作并保留证据，不盲目重试。已明确的原协议查询与恢复流程可在安全边界内继续；其他独立证据评审不因此停止。

### A0-1 数据库迁移与启动保护

**原文保证：** 数据库迁移可重复执行；数据库 schema 落后于代码时拒绝启动。原文没有指定文件计数、校验和或大小版本兼容方案。

**实际怎样做：** [迁移实现](../apps/server/src/core/migrations.ts)从文件名解析正整数显式编号，按数值排序，允许编号间隔，拒绝重复/非法编号；目标版本为最大显式编号。SQL 原始字节读取后计算 SHA-256，同一内存快照用于执行与记账。迁移前逐条核对 `schema_migrations` 的编号、名称和 checksum，历史必须构成当前清单的完整前缀才可追加；启动要求完整清单全等，落后或更高均拒启。[迁移脚本](../scripts/migrate.ts)与启动使用同一事务级 advisory lock；本批 SQL、ledger 初始化和记录同事务提交，失败整体回滚。

**必须披露的前提：** 普通迁移默认拒绝缺 checksum 的旧 ledger，不自动给旧记录背书。现有六版库须按[显式基线流程](core-migration-integrity.md)与固定 `fa1baa7` 六份 SQL 清单及独立参考库实际结构比对；通过只证明此次观察的结构一致，不还原历史执行字节。该流程需停旧服务、无其他非协作 DDL 和 CREATEDB 权限，结构比对也不涵盖业务数据、所有权/ACL及全部PG配置。常规启动核对可信发布物与可信账本，不逐次穷举物理结构，也不能防御管理员同时改文件和账本。

**007升级边界：** 旧版 running 序列必须先在旧版自然完成，再停服务、基线化并迁移；007遇running拒绝且不回填旧sent观察时间。旧记录保持NULL，不用updated_at或重放时刻伪造历史。已完成007的新版本普通重启不重新执行此升级保护，新机制下已持久观察时间可以恢复。隔离备份副本演练与真实演示升级分开；二者升级前running均为0，不把该结果解释成实测了旧running自然完成，详见[E14](acceptance-evidence-index.md#e14)。

### A0-2 统一错误响应

- **实际机制**：[AppError/RemoteError](../apps/server/src/core/errors.ts)区分本地和远端错误，[app错误处理](../apps/server/src/app.ts)输出错误对象及请求标识，业务错误保留附加字段。401/403分别固定为 `UNAUTHORIZED/FORBIDDEN`；RemoteError映射502并保留远端错误码，其他未预期异常映射 `500/INTERNAL_ERROR`。
- **用例先审**：从原文2.3的错误状态和业务字段逐项映射，包含参数错误、未登录、只读写入、资源不存在、状态冲突、变量预检失败及内部错误；检查HTTP状态、非空 `error.code/message/requestId`和该业务所需字段，不能只查“有error”。
- **证据及边界**：[E01](acceptance-evidence-index.md#e01) `error-envelope`覆盖15类代表结果；后续新增群资料冲突另有[专项](group-profile-conflict-review.md)。代表错误覆盖不是所有输入组合全测，实际枚举以测试和JSON为准。
- **负责人判断**：错误能否指明业务原因和后续处理；是否有用统一包装丢失必要详情的情况。当前材料供评审，未自动填负责人通过。

### A0-3 登录与只读权限

- **实际机制**：[认证模块](../apps/server/src/core/auth.ts)使用持久会话与凭证哈希；每次认证核对会话/凭证有效性。受限业务路由在处理器执行前要求管理员权限，按钮隐藏只是界面约束。
- **用例先审**：两个预置身份可登录；缺失/无效凭证401，有效viewer所有受限业务写入403、读取可用。先对照真实注册路由再枚举请求，每项比较业务快照和外部调用增量，证明403发生在产生业务效果之前。
- **证据及边界**：[E01](acceptance-evidence-index.md#e01)对固定基线9条受限POST/PATCH逐一检查，生产进程重启后凭证/权限仍有效；后续条件资料更新沿用独立专项。登录、续期和注销不是被禁止的业务写。15分钟TTL检查采用存储间隔及到期边界，没有实等15分钟。
- **负责人判断**：接口清单是否完整，资源是否真实有效，是否因其他参数错误提前返回而掩盖权限问题；会话并发及身份切换继续看B3。

### A1 账号状态与事务

- **实际机制**：[Accounts.transition](../apps/server/src/modules/gateway/accounts.ts)锁定账号行，再检查合法边和条件来源；[changeAccount](../apps/server/src/modules/gateway/state.ts)将本地终态副作用与事件写入同一事务。限流释放会在锁内重新核对状态及期限。远端connect/disconnect调用与本地事务是两个系统，不能声称一起回滚。
- **必须审的用例**：完整转移表、同一来源的两个并发合法修改只成功一个；重复终态事件无新增效果；终态时账号/成员/排队消息/序列/事件一致；事务失败全回滚；限流等待期间转离线或再次限流，不被旧到期处理错误恢复。
- **证明与缺口**：[E02](acceptance-evidence-index.md#e02)/[E04](acceptance-evidence-index.md#e04)保留状态机及事务证据；[E10](acceptance-evidence-index.md#e10) V-ACC-01用真实HTTP远端成功和PG写入故障复现两侧不一致。新增日志与尽力写入的 `account_result_unknown` 一致性事件只诊断，API仍失败；不补偿、不自动改状态、不提供结果查询，崩溃及诊断库写入失败仍有窗口。
- **负责人重点**：本地不变量与远端一致性的保证分别到哪里；已完成补证的有限场景不代表所有跨系统窗口闭合。

### A2 发送、确认和事件恢复

- **实际机制**：[Messages](../apps/server/src/modules/gateway/messages.ts)先持久化出站记录，再由每账号互斥工作循环串行处理；远端调用前记录sending/尝试信息，返回后另行更新。已受理不等于已发送。明确504后进入确认：当前要求从记录超时起至少2100ms后**发起**的查询返回404，才可授权一次重发；旧查询迟到404不能授权。没有明确504且结果未知的崩溃窗口保守停在待确认。
- **事件机制与前提**：[GatewayEvents](../apps/server/src/modules/gateway/events.ts)从 `since=0` 重放，eventId去重与业务更新同事务；SSE现先累积跨块文本再归一CRLF分帧，已复现并修复跨块分隔符问题。成员事实仍在群锁内远端查询，单次读取超时2秒并保留失败重试；多次慢事件和整体队列仍可能延迟，见[E10](acceptance-evidence-index.md#e10)。依赖网关保留历史，自身回流不触发Agent。
- **必须审的用例**：正常发送/自身回流只一条；两种504、查询503后恢复、迟到404、重发次数上限；按原文区分504后5秒内收敛与查询恢复后2秒内更新的计时起点；账号限流与错误分类；重复/乱序事件、写库失败后重试、停机期间补投。同时对比数据库身份和网关实际效果，数据库一行不能证明远端只发一次。
- **证明与缺口**：[E02](acceptance-evidence-index.md#e02)发送与可靠性回归、[E04](acceptance-evidence-index.md#e04)子进程强制终止后补事件。CG03/L1仍缺“无明确504且远端结果未持久化”的可判定恢复，不能用其他崩溃点通过替代“任意时刻”保证。

### A3 异步建群

- **实际机制**：[Jobs](../apps/server/src/modules/gateway/jobs.ts)持久化阶段并在任务锁内推进；join的202不等于入群事实，确认超过10秒失败。promote首次明确503计一次、500ms后仅重试一次；首次NOT_MEMBER_YET仍有限重试，第二次503/NOT_MEMBER_YET落失败且总调用不超过两次。超时、断连接或结果保存失败仍按未知效果暂停，不当作安全503。
- **必须审的用例**：顺序记录create→invite→join受理→对应成员确认→promote；群主无joined事件仍入表；多成员角色与失败步骤正确；无确认超时失败；重启后从持久阶段推进，不重复已确认步骤。
- **证明与缺口**：[E02](acceptance-evidence-index.md#e02)/[E04](acceptance-evidence-index.md#e04)保留正常及状态证据；[E10](acceptance-evidence-index.md#e10)真实HTTP验证promote503恢复、失败及未知边界。历史时间夹具不冒充实等10秒；CG04/L2远端已建群但ID未存仍无法无歧义恢复。
- **负责人重点**：状态依据是远端受理、成员事实还是本地推断；每个外部调用和本地提交间的空窗分别如何处理。

### A4 消息快照与实时推送

- **实际机制**：[消息查询](../apps/server/src/modules/gateway/index.ts)首请求将当前群全部消息按 `sent_at DESC, id DESC` 排序并保存DTO快照，游标携带快照ID和偏移；后续页读取同一快照，不是群目录的创建时间keyset分页。[useTimeline](../apps/web/src/hooks/useTimeline.ts)实时变化时读完整新快照，按稳定内部消息ID合并；[历史续页保护](../apps/web/src/hooks/loadEarlierTimelinePage.ts)用页面代次/快照修订防止迟到页覆盖新结果。
- **WS机制**：[realtime](../apps/server/src/core/realtime.ts)认证后按持久seq补发事件；每次轮询重新鉴权。提交后的事件可见性依赖[数据库事件事务](../apps/server/src/core/db.ts)，不能先推送再提交。
- **必须审的用例**：同时间不同消息、历史补投、queued回流改为sent、分页同时新消息到达、旧续页成功/超时迟到、未认证连接无业务帧、seq单调。最终比较**ID集合、字段状态和顺序**，不只比条数。
- **证明与缺口**：[E02](acceptance-evidence-index.md#e02)、[E07](acceptance-evidence-index.md#e07)CG12包含定向及浏览器证据。完整快照的存储/重读成本是当前实现前提，大规模性能不能由小规模结果外推；恢复到页面呈现的时限继续看B4。

### A6 页面1–3与业务状态一致性

- **实际行为**：页面展示服务账号状态、群角色、消息投递状态及最近Agent运行；管理员与viewer入口不同，但后端鉴权仍由A0证明。已修复的发送账号失效场景保留原选择和草稿，不能悄悄换成另一个在线账号。
- **必须审的用例**：合法操作可用，非法状态有正确原因；提交账号与结果发送者一致；queued/unknown不显示为sent；blocked及失败信息可定位。页面操作与数据库/外部记录使用同一业务身份关联。
- **证明与缺口**：[E07](acceptance-evidence-index.md#e07)CG01/19及历史浏览器记录。用户已确认的一条手动消息只覆盖该条正常流程，不等于全部页面边界验收通过；新增群资料能力不替代核心页面要求。

### B1 变量、序列互斥与确认后排期

- **变量和账号机制**：[Sequences](../apps/server/src/modules/automation/sequences.ts)在启动前解析并预检所有步骤，保存解析后的文本、变量值及来源；推进时使用保存值。步级非空值从该步持续继承，直到后续再次覆盖；第2步赋值、第3步空串时，第3步仍取第2步的值及来源。发送候选先选online；admin角色任务优先群管理员、其次群主，再按账号ID，member任务按账号ID；只有限流候选则等待，没有对应角色候选才跳过。
- **并发和时间机制**：群行锁与唯一索引约束单群running。收到显式message_sent进入处理时先采集本地时刻，成功事务将首次值写入 `messages.message_sent_observed_at`，下一步从此值加delay；回流或query先变sent不能提前推进，重复事件不覆盖。skip仍用实际跳过时刻，不用网关sentAt。新调度锁持有者先补认已完成效果，再重排当前最早逾期且未入队步骤；锁等待超时保留待接管义务，完成前不普通推进。
- **必须披露的前提**：V-SEQ-01已只读核清：当前运行vars/stepVars及定义固定，启动预计算与该输入下发送时计算等价；未新增动态重算。观察时间在同进程失败重试保留，成功持久后重启可恢复；**首次接收尚未持久便硬死，准确原接收时间仍不可还原**，不能把普通排期修正外推成R09任意中断保证；多实例全局最早观察也未证明。旧running升级遵守A0-1的007门槛。
- **必须审的用例**：默认空串忽略与步级空串不覆盖；来源步号准确；第3步缺变量则整个启动run0/send0且可重试；同时启动一201一409；角色顺序、限流等待/跳过；下一步从真实确认或跳过起算；重启不把后续所有步骤都重排。
- **证明与缺口**：E02/E05/E07保留各自版本证据；[E11](acceptance-evidence-index.md#e11)新增回流先到、query先确认、message_sent后到、重复、重启、普通及skipped排期和锁住接管场景。精确排期断言停在queued，不冒称已经远端发送；首次接收未落库硬死窗口仍开着。

### B2 邀请与退出群组

- **实际机制**：[Jobs](../apps/server/src/modules/gateway/jobs.ts)区分邀请未就绪、过期后的有限重取与已经在群；退出任务先处理非群主，失败后继续其他非群主，保留群主。各步骤存储结果，确认退出后的成员对账再决定完成。
- **必须审的用例**：未就绪等待、过期最多重取一次、ALREADY_MEMBER查询确认；一个非群主失败时其余人仍推进且群主未退；错误步骤/最终成员清楚；群left后的公开成员视图与远端事实范围一致。
- **证明与缺口**：[E02](acceptance-evidence-index.md#e02)生命周期与membership用例。CG07仍需澄清：公开left后members为空，远端可能保留外部成员，完成快照可记录外部成员，但不等于公开接口仍镜像远端全体；不能由工程侧替负责人接受条款偏离。

### B3 凭证轮换与请求身份隔离

- **实际机制**：[服务端](../apps/server/src/core/auth.ts)仍用HttpOnly refresh cookie、持久轮换、旧凭证重放撤销及注销；协议未改。[客户端](../apps/web/src/api/client.ts)普通请求与重试绑定发起会话代次，旧成功/401不能跨新身份重放或清新会话，WS旧失败不再直接清会话。同页login/logout/refresh共用串行队列，前次完成或原20秒超时结束后才发后次请求；REST/WS按代次共享singleflight。
- **cookie边界单独证明**：浏览器收到响应头就处理Set-Cookie，内存代次检查不足。旧refresh200或401均须先完成，才能发logout和新login；退出可使用前序更新的凭证，必要时在本次队列内续期一次后撤销，旧401不令队列死锁。网络/超时失败释放队列；不声称abort会回滚服务端。保证限本页正式入口，多标签协调不在本轮。
- **必须审的用例**：旧业务请求/重试迟到不以新身份执行；旧refresh响应200/401后新登录cookie仍有效；真正整页重载后仍为新身份；同页REST/WS仍只续期一次；超时后可继续，logout实际撤销或已失效才收口。
- **证明与缺口**：[E12](acceptance-evidence-index.md#e12)保留代次及cookie修前失败，并有受控fetch、真实20秒超时和隔离真实浏览器200/401释放→新登录→整页重载通过。浏览器版本单列，不能只凭当前页仍显示viewer证明cookie安全；[E07](acceptance-evidence-index.md#e07)同身份CG17为历史独立证据。

### B4 断线恢复至实际呈现与步骤详情

- **实际机制**：WS按已处理seq恢复，页面变化驱动[snapshotReconciler](../apps/web/src/hooks/snapshotReconciler.ts)串行重读；失败保留dirty，自动从250ms退避至2秒上限，即使没有新事件也重试。时间线读完整新快照后再应用；步骤详情显示输入、返回、审计和协议错误原文。
- **必须审的用例**：断线期间新增和旧时刻消息补投，重连后第一次REST失败，没有后续新事件和手动刷新仍补齐；比较最终ID集合及顺序，从连接实际恢复可用计到页面可见，不能把WS收到事件当结束。原文协议响应在页面可查，blocked可辨认。

## 五个需要深入理解的关键点

技术审查重点是业务规则、失败位置、实现依据与剩余边界。每项结论应能追溯到相应机制和验证证据。

| 重点 | 要能说明的问题 | 应查看的最少材料 |
|---|---|---|
| **本地事务与外部效果的边界** | 数据库事务为何不能直接回滚网关已发消息？哪些情况可以查询确认，哪些情况只有保守暂停？ | A2/A3/A5 的一条正常时序、一条结果丢失时序、持久意图及 CG-03–06 |
| **幂等身份与并发互斥** | eventId、msgId、clientMsgId、tool_use.id、idempotency_key 各解决哪一层问题？部分唯一索引/锁防什么竞争，又不保证什么？ | 一条消息从提交到回流的关联；一次同 key 重试；一次被确定触发的数据库并发窗口 |
| **失败默认不执行与事务完整性** | 审计超时、非法结果、账号终态、任务接管时，什么证据证明没有越过保护？ | 当前工具实际外部调用次数、事务前后记录、提交后事件；不能只看返回状态 |
| **时间、顺序与恢复** | sentAt、受理时间、排期基点和活动预算有什么区别？何种时钟/故障窗口已测，哪些误差仍存在？ | 明确504的查询时序、序列前后步时刻、活动计时及 CG-08；真实等待与模拟时钟分开 |
| **前端显示与事实一致** | 去重键、补投与分页怎么组合？过期响应如何隔离？什么时刻可以清除提示或判定已同步？ | 请求与 WS、客户端合并、最终可见 ID/状态的对应证据；B3/B4 的真实页面记录 |

优先选三个已有深入证据的例子：迟到 404 不能授权重复发送、审计 blocked 与工具状态原子提交、同页重连后页面补齐。历史修前失败/修后通过若已有原始日志，可直接审查，无需重复制造同一缺陷或修改产品。

## 如何判断用例和结果可信

| 审查层次 | 必须回答 | 不足以证明的材料 |
|---|---|---|
| **用例有效** | 预期独立来自原文；用例真的触发所说竞争/故障窗口；断言检查最终业务记录、外部效果和必要时限；对应错误实现是否会失败 | 测试只复述实现；只返回200；只用 Promise.all 而不能证明目标事务相遇；模拟器事先替产品做了去重 |

## 批次三：序列预检与运行（约 10 分钟）

在“定时序列”选择批次一的群。管理员可创建以下短序列：

```json
{
  "name": "活动通知验收",
  "steps": [
    { "index": 1, "accountRole": "admin", "text": "{event} 将于 {time} 开始", "delaySeconds": 2 },
    { "index": 2, "accountRole": "member", "text": "{event} 资料位于 {location}", "delaySeconds": 1 },
    { "index": 3, "accountRole": "admin", "text": "{event} 由 {owner} 负责", "delaySeconds": 1 }
  ]
}
```

默认变量：

```json
{"event":"发布沟通","time":"20:00","location":"默认资料区"}
```

第一次使用以下分步变量，点击预检：

```json
{"2":{"event":"第二场","location":"共享盘/第二季度"}}
```

预期缺失第3步的 `owner`，显示 `UNRESOLVED_PLACEHOLDER`、stepIndex=3、key=owner；不出现running记录，也不发送任何一步。随后补齐：

```json
{"2":{"event":"第二场","location":"共享盘/第二季度"},"3":{"event":"","owner":"值班同事"}}
```

预检弹窗应显示：

| 步骤 | 最终消息 | 关键来源 |
|---|---|---|
| 1 | 发布沟通 将于 20:00 开始 | event/time 来自 default |
| 2 | 第二场 资料位于 共享盘/第二季度 | event/location 来自 step:2 |
| 3 | 第二场 由 值班同事 负责 | event 继续来自 step:2；owner 来自 step:3；空字符串不清空event |

## 批次六：浏览器断线补齐与分页

1. 打开已有多条消息的群，记下当前消息标识及时间。
2. 只将此浏览器标签页设为离线；在终端向模拟网关注入新消息，包含一条很早的sentAt，必要时超过50条以跨页。
3. 恢复标签页网络，记录恢复时刻。页面应显示连接恢复过程，随后补齐期间消息；测量从网络恢复到可见的时间，目标≤3秒且没有重复行。
4. 在新消息写入时加载更早，核对稳定消息id和数量。实时完整快照核对后历史可能已全部载入，此时不再出现“加载更早”。
5. 对照原快照语义：分页固定的是一次读取的成员集合；新补投和状态变化在后续快照合并中展示，不被悄悄塞入旧快照游标。

## 关键设计理解与排查

| 主题 | 应能说明的机制 | 证据与排查入口 |
|---|---|---|
| 账号终态 | 状态、成员、排队消息和序列步骤在同一事务改变；无终态出边 | `gateway/state.ts`、account_terminal、G02 |
