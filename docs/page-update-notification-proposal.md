## 已确认要求与范围

本次仅要求评估和修订原提案，没有“开始实现”指令。用户已选前台与清除策略，尚在评估扩大的覆盖范围和成本；不得把“复杂度可接受就可以做”的条件句记成实施授权。

用户要求：浏览器页面**未聚焦时，当前已打开页面的相关实时更新必须提示**。本轮扩大的是“哪些页面可作为 scope”：账号列表可以提醒账号状态，群目录可以提醒自身结果变化；两者仍不直接提醒群消息（消息引起本页可显示的运行状态变化则按运行变化处理）。提醒与页面类型、实体 ID、当前选择及筛选上下文匹配，不做全系统群未读汇总。

“有更新”是当前标签页、当前页面生命周期内的关注状态，不是服务端未读数、阅读回执或跨设备已读系统。建议用户离开路由或主动更换查询/实体上下文即销毁旧 scope，返回重新订阅；刷新数据与加载更多本身不重置 scope。整页刷新重新开始，不为离开期间补记提醒。多标签页独立，关闭页面后不提醒，不请求系统通知权限，不加声音、Web Push 或 Service Worker。

本次只修订本文件；群名称、简介、创建时间不重做，不接管正在实施的分页/资料交互工作。其他分支提醒草稿不视为已采纳设计。既有全局异常提示保持独立；页面关注状态清除不代表异常已处理。

**已选交互的建议表达：**采用静态二值提示，避免伪装成准确未读数量。标题示例为 `[有更新] 群详情 · Kapibala`；恢复后为 `群详情 · Kapibala`，不把消息正文放进标题。聚焦且正在看新内容时不再加标签提醒；未呈现的更新合并成一个页内入口，不重复 toast、不抢焦点、不强行滚走正在阅读的历史。

系统通知可让用户在看不到浏览器时更容易发现变化，但增加权限与平台策略；声音有打扰和播放限制；后台推送需要服务端投递及订阅生命周期。三者仅作后续备选，本轮不纳入。

## 页面作用域与五种状态

建议 scope 为 `{ pageType, entityId, contextKey, sessionEpoch, generation }`。列表 entityId 可为本页集合标识；contextKey 来自实际生效的筛选/选择条件，不取尚未提交的输入草稿。epoch/generation 隔离重新登录及 A→B→A 的旧响应；不要用易歧义的字符串拼接。

| 状态 | 定义 | 不代表什么 |
|---|---|---|
| route active | 当前 Workspace 真正渲染这个详情 ID | 后台浏览器标签内也可以保持活动路由 |
| document visible | `visibilityState === 'visible'` | 不代表获得焦点或看到某条消息 |
| document focused | `document.hasFocus()`，监听 window focus/blur 后重算 | 不代表有真实操作，更不代表阅读 |
| 用户交互 | scope 内可信点击/键盘输入/触摸或滚轮引发的主动滚动 | 鼠标移动、程序滚动、定时器或自动聚焦不算 |
| 内容已呈现 | 对应更新实体已成功加载、React 已提交，目标区域进入实际视口且未被应用弹层挡住 | 数据请求成功、在 DOM 中、列表在底部均不能单独证明 |

前台条件为 `routeActive && visible && focused`；失焦提醒条件为 `routeActive && (!visible || !focused)`。就算标签页被切到后台，路由仍是群 A，所以可提醒 A；在同一标签内导航到群列表，则 A 的 scope 已结束，不再提示 A。

本轮覆盖候选以如下矩阵为准，替代上一版“首版只接群消息”的范围建议。页面组件注册唯一 owner，嵌套列表、任务面板和运行面板是它的目标区域，不能各自抢占标题。

## 页面覆盖矩阵：范围建议与现状证据

“可显示变化”是业务字段或结果集合变化，不是对象引用变了。事件先用于定位/失效，再对允许的字段或集合投影比较；已知语义明确的事件可先提示“内容待同步”。不能凭每次 revision、每次轮询、更新时间戳或重新排序得到的新数组触发提醒。

| 当前页面与 scope | 值得提醒的变化与目标定位 | 现有事件是否够用 | 呈现确认依据 | 最小补充/接线 |
|---|---|---|---|---|
| 账号 `accounts / collection` | accountId 对应的 status、platformUserId、rateLimitedUntil 实值变化；非倒计时数字跳动 | account_status_changed 有 accountId/from/to；account_terminal 重复覆盖同一终态，需合并。限流同状态续期当前不发状态事件 | 对应行当前状态/时间可见后操作该区；多个状态已被后来状态覆盖时显示“期间状态有变化，当前…”摘要再确认，不假称看过中间态 | 复用 [Accounts](../apps/web/src/pages/Accounts.tsx) 的成功快照；同状态字段变化可新增 account_changed，不能伪造 from=to 的状态转移 |
| 群目录 `groups / collection / q+order+pageSize` | 新增/移出匹配结果、排序位置、卡片实际展示的名称/简介/状态/成员数/开关/活动运行摘要；groupId 或整个查询结果 | group_changed 只有 groupId（部分含 status），不能判定字段变化/搜索匹配；agent_run、sequence_run 可影响卡片；account_terminal 可影响成员数。单纯 message 不算目录变化 | 已加载卡片具体变化按行确认；未加载位置或集合变化按“结果范围”确认，见下一节 | 只消费分页控制器的 relevant/stale/成功呈现状态；必要时补 group_changed 的实际字段分类，未知关联先失效核对，不另建查询缓存 |
| 群详情 `group-detail / groupId` | 消息逻辑 ID；资料字段；成员以 platformUserId 定位并比较 role/accountId；开关/群状态；最近运行摘要按 runId；当前退群 jobId | message 已有但创建/回流混用；group_changed 可触发重核但无具体字段；账号终态跨群后果应核对此群成功快照；agent_run 可定位最近运行 | 消息按原规则；资料/成员/开关只确认对应区域；移除的成员用“成员列表已更新”摘要，不能等待消失的行进入视口；运行/任务各确认各的结果区 | 一个群详情适配器分目标 key；继承消息契约补充，其他字段先投影比较，避免把本页一个点击当全部确认 |
| Agent 列表 `agent-runs / selectedGroupId` | 当前选择群新增运行、已有 run 的 status/endReason/recoveryNote 变化；最近 100 项移出也属结果变化 | agent_run 有 runId/groupId/status/endReason，适用于运行创建/结束；不包含步骤号。pause 的 inconsistency.ref 需按 kind 定位并重核 | 具体运行卡片或“最近运行列表已更新”范围摘要；纯步骤变化而卡片不变不提醒 | [AgentRuns](../apps/web/src/pages/AgentRuns.tsx) 的本地选择变化必须更新 scope；复用 [AgentRunList](../apps/web/src/components/AgentRunList.tsx)，不改变最近 100 条限制 |
| Agent 详情 `agent-run-detail / runId` | 运行终态/摘要/恢复说明；步骤首次可见、结果/错误/审计结论变化，目标 `(runId, ordinal)` | **不够**：当前 agent_run 无 ordinal，也未在普通步骤插入/完成逐步发事件；详情靠 1s 轮询。toolUseId 可为空，不能单独当步骤 ID | 对应步骤头/已变字段区实际呈现；折叠 rawResponse 未展开不能确认只存在于其中的变化。终态卡与步骤各自确认 | API 可加可选 ordinal（已有数据库字段），新增 agent_step_changed 或等价可选 payload；在提交可显示步骤变化的事务补事件，不推审计重试/心跳 |
| 序列选择与运行 `sequences / selectedGroupId / selectedSequenceId` | 群/模板选择集合变化；所选模板内容；展示中的 runId、步骤 `(runId,index)` 的 status/scheduledAt/sentAt/clientMsgId 与实际展示字段；运行终态 | sequence_run 有 runId/groupId/status/currentStepIndex，**currentStepIndex 不是变化步骤版本**。accepted、clientMsgId 写入、恢复改排期不全有对应 run 事件；模板创建无事件 | 下拉集合变化用“可选项已更新”范围摘要；当前模板定义区/运行步骤区分别确认。被新运行替换的旧运行终态用摘要保留，不默默丢掉提示 | [Sequences](../apps/web/src/pages/Sequences.tsx)+[SequenceProgress](../apps/web/src/components/SequenceProgress.tsx) 共用 owner；补 sequence_definition_changed、stepIndex/changedFields 或 sequence_step_changed，run 状态不改 |
| 当前页嵌入的建群/退群任务（非新路由） | 当前实际挂载的 jobId，完成/失败、errors/recoveryNote；不提醒未打开任务 | [JobProgress](../apps/web/src/components/JobProgress.tsx) 800ms 轮询，没有通用 job_changed；已有 group_changed 不保证覆盖失败 | 当前任务状态/错误摘要已呈现并操作；隐藏面板是结束该目标，不是读完所有结果 | 最小为成功快照差分；需要同等持久重放保证则在任务终态/错误变更提交处补 job_changed，纳入完整成本 |

登录、会话恢复屏、错误占位与静态文档不为凑数接入。选择器未选定实体时仅注册集合目标，不能订阅任意默认 ID；以页面最终实际渲染的选择为准。序列 URL 的 id 是 groupId，不是 runId，运行 ID 必须取页面实际展示来源（activeSequenceRunId 或该群已保存的 runIds）。

**范围变化的规则：**用户主动切群、换搜索/排序/每页大小或选序列时递增 generation，旧回调失效；加载更多只扩展已加载范围，不建立新 scope。后台自动出现新 run、旧 run 终结或列表自动刷新不是用户换 scope，不能借此丢掉待关注项；适配器把已消失目标转换成明确的结果摘要。详情按精确 runId 过滤，不能因为 runId 属于同群便接受另一个运行。

## 列表、分页过期与呈现：沿用同一个数据负责人

群目录分页正在另行实施：pageSize/cursor/order/q、服务端搜索名称/简介/两个 ID、创建时间与 ID 固定排序；第一页自动刷新，多页遇相关变化标过期、禁止继续旧 cursor。这里是本轮提供的集成约束，非本分支已验证实现。保留旧 GET /api/groups 和 Sequences 消费者，不借提醒再次调整查询协议。

**职责分界：**分页控制器决定查询身份、相关性、stale、游标可续接性、刷新成功与渲染版本；attention 只消费这些事实，提供标签提示和待确认状态。用原来的过期提示作为同一个页内入口，不再额外叠一条“新消息”横幅。attention 的确认不能清 stale、恢复旧 cursor 或改列表缓存。

| 列表情况 | 提醒与清除建议 |
|---|---|
| 已加载且当前可见记录字段变化 | 复用自动刷新；确认对应卡片/行的已变字段和版本，不影响其他待关注目标 |
| 已加载但视口外 | 保留“有更新 · 查看”，定位目标后确认；点别的卡片或编辑表单不代为清除 |
| 新增/删除/排序变化，影响当前查询但不在已加载部分 | 建立 `query-result` 范围候选，提示“列表结果有变化”；刷新后显示新第一页/空态及“已刷新当前筛选结果”说明，凭该次真实刷新操作和呈现确认，不逐条追踪全表 |
| 变化明确在当前筛选之外，前后都不匹配且不影响可见集合 | 不生成 attention；若记录原来匹配、修改后移出，仍是本查询变化 |
| 只有 groupId，无法确定未知记录是否影响查询 | 沿用控制器保守 stale，明确“列表可能有变化，请刷新核对”；失焦可用 `[待刷新]`，不伪称已经发现新记录。刷新核对成功后的范围呈现可确认。若需严格零无关提醒，需服务端按查询判断影响，成本另计 |
| 第一页自动刷新成功 | stale 可由控制器解除，但 attention 仍需对应内容呈现+用户操作；已选前台策略保持不变 |
| 多页已 stale | 禁止续接旧 cursor；“刷新结果”交给控制器重开第一页。成功后看到新结果/空态再确认该批范围候选，失败则两种状态都保留 |
| 用户换筛选/排序 | 结束旧 scope，不将其记为已读；新范围重新建立起点，初始结果不提醒；浏览条件保存由原分页功能负责 |

不得在 attention 内重写服务端 q 匹配器、维护第二份全表快照或请求所有页证明“没变化”。若控制器尚无可靠相关性，输出 unknown，不自行宣称 irrelevant。已知成员、活动运行等变化也可能改变卡片但不改变搜索成员集合，按卡片展示字段比较后决定。

在详情页，“只有某个 target 返回 404”不等于整个页面实体失效：运行被替换、成员消失、嵌入任务不可用只处理该目标和范围摘要；只有页面主体确定无权限/不存在才退出整个 scope。

需要从既有数据 hook/分页控制器取得的最小事实为：`queryKey / generation / stale(reason) / lastSuccessfulSnapshot(requestId, coversSeq) / renderedVersion`，及本次成功快照的业务投影；命名可适配正在实施的接口，**不是要求该线程现在顺带实现提醒**。当前 useResource.reload() 会捕获错误并返回 Promise，Promise 结束不证明数据更新成功，必须读取明确的成功提交证据。

coversSeq 只能是**发起该次读取前**已接收的候选事件边界，不是响应回来时的最大 seq。刷新过程中又来事件，应继续置脏并读取下一版本；不能一次点击确认后到的变化。重试成功要能重新提交成功证据，不能把本次失败留下的旧 data 当作新结果。

账号列表、Agent 最近运行列表及序列选项集合采用同样的范围规则，但不强行加入分页框架。范围确认表示“用户已得知这个集合更新并查看了刷新结果”，不表示所有记录都读过。超出最近 100 项、被筛选排除、已删除、被后来状态取代的目标，以结果摘要替代不可达节点；加载失败仍不可确认。

## 触发与清除矩阵（已选原则，具体接线仍为建议）

“提示”只针对矩阵允许的业务变化；以下消息规则保留，其他页面换成对应字段/区域或上节范围证据。加载失败/断线仍使用相应错误或连接提示。

| 场景 | 标签标题/favicon | 页内状态与清除 |
|---|---|---|
| 当前 scope 已订阅，失焦收到相关新消息 | 立即设置静态提示，不等待内容渲染 | 记录待关注 ID；即使加载失败也保留，显示“有更新，内容待同步” |
| 前台收到新消息，内容尚未呈现或正在看旧消息 | 不新增标签提示 | 一个“有新消息 · 查看”入口；不得因持续打字而清除未见消息 |
| 前台新内容已呈现，持续在该消息区域交互 | 不新增标签提示 | 当前呈现的更新可确认；不弹窗、不闪烁 |
| 前台新内容已呈现，但没有更新后的真实操作 | 不新增标签提示 | 留待确认；之后失焦仍有待关注项则显示标签提示 |
| 失焦提示后仅切回/窗口获得焦点 | 已有标签提示保留 | 不把 focus/visibilitychange 当作确认；提供页内入口 |
| 在消息区点击/键盘操作，或用户滚动使目标呈现 | 仅在待关注集合清空后恢复 | 只确认该次操作时已呈现的更新；不清除视口外或加载失败的项 |
| 点击“查看” | 定位完成且对应内容呈现后逐项清除 | 默认定位最早待关注项；剩余项保留入口。“查看”失败不清除 |
| 输入框打字、发送消息、操作群资料/设置、点导航 | 不作为消息确认 | 发送后的自动滚动也不能把所有消息自动标为已关注；离开路由执行生命周期清理 |
| 本标签用户主动手动发送 | 不因自身消息创建/回流新增提示 | 通过预先登记的 clientMsgId 匹配，不按文本或 isOwn 猜测 |
| Agent/序列后台新增消息，或其他标签手动新增消息 | 按当前前台/失焦规则 | 都是本页新变化；同一记录后续发送状态不重复提示 |
| 首次历史、加载更早、重复事件、相同快照 | 不新增提示 | 初始化不等于已读操作；历史不加入待关注集合 |
| 切群 A→B、离开详情、退出登录或会话失效 | 恢复对应页面基础标题和正常图标 | 取消旧 scope、清空待关注项与自身发送集合，拒绝旧回调 |

呈现判据建议先用消息行正文区域与顶层视口/滚动裁剪的实际交集，超长消息至少有可阅读的正文片段，而非仅头像/行尾。可用 IntersectionObserver 辅助，操作时再核验当前布局；弹层打开时不自动确认。这个判据表示“更新已被呈现且用户有相关操作”，不宣称全文读完。阈值需浏览器验收后微调。

用户操作只能确认其捕获的那批 ID/版本；同一时刻新到的消息不能被一次 `clearAll()` 抹掉。程序化滚动需有“查看”按钮发出的明确操作令牌，普通 scroll 事件本身不足以证明用户滚动。不得在更新前的任意点击后长期自动清除未来消息。

## 去重、初始化与重连：建议的最小可靠路径

推荐复用现有 WS 和快照，不新建提醒 socket、不建通知中心、不写已读表。为解决已核实的协议缺口，评审后增加以下小范围契约；这些尚未实现。

1. **页面订阅起点。**在已认证 WS 增加一个无持久化的 marker 请求，携带 requestId。服务端读取已提交事件最大 seq 并返回 `scope_ready { requestId, startSeq }`；这是本次订阅成立的边界。前端进入已接入页面或用户更换 scope 即请求并缓冲候选事件，拿到对应 marker 后仅接收 `seq > startSeq`。控制消息不推进全局 lastSeq，不能跳过其他尚未消费事件。marker 不创建服务端未读状态，也不改变现有全局事件传输。
2. **业务变化类型。**新写入的 message 事件增加 `changeKind: 'created' | 'delivery'`。真正插入新记录时是 created；accepted/sent/失败及身份确认是 delivery。继续携带 groupId/id/clientMsgId/msgId；可附 source 帮助解释，但不把 source=manual 等同本标签用户。入站重复插入失败不再造 created。旧 payload 缺字段只能促使刷新，不能直接升格为新消息提示。
3. **本标签发送关联。**手动 POST 前生成 clientMsgId 并登记在当前 scope；发送 API 接受该可选字段，复用已支持它的 enqueueSend。这样 WS 先于 POST 响应也能准确排除本次自身发送。需校验 ID、拒绝冲突，不因此新增自动重发行为或承诺新幂等语义；其他消息仍正常提示。请求结果不确定时保留这个精确 ID 至 scope 结束，不能暂停整页消息提醒。
4. **事件与呈现分开。**身份已确认的合格 created 事件先写待关注集合，再让既有 revision/快照链路加载正文；首次快照不能顺便清掉这些项。快照中的历史不凭数组差异触发。新消息 sentAt 即使很早，仍按新提交事件处理。快照请求失败不能确认；重试成功后再允许用户确认。
5. **断线重放。**同一 scope 保留原 startSeq、候选项及去重记录，按既有 sinceSeq 恢复，不重新建立起点从而吞掉断线期间更新。同一 seq 只消费一次；同一消息身份只创建一次关注项。其他实体事件只刷新其原有数据路径，不进入本 scope。只有切换路由、用户更换筛选/实体上下文或切换会话才重置订阅起点。

消息逻辑身份优先关联本地 id，辅以 scope 内的 clientMsgId 与 msgId 别名；同一出站消息的临时回显与最终 outbox ID 要归并，不能因为确认后换了标识再次提醒。现有 findEcho 会向网关核对身份，但查询 404 后可能暂时按独立回显落库。因此业务新消息候选不能仅由“插入了一行”推断：有待关联出站候选的服务账号回显应暂缓业务新消息判定，待权威关联结果后按原消息归并，或确认独立消息后再产生候选；不能凭相同文本或一次 404 判定来源。这个分支必须在实施前用隔离竞态测试验证，若现有网关无法提供足够关联证据，应明确保留身份待确认限制，不宣称完全消除误报。只比较消息条数、sentAt 最大值、isOwn、最后一次 revision 都不够。提醒身份待确认只能限制候选分类，不能延迟/丢弃原 message 事件、消息落库、时间线同步或 Agent 原有触发；若解决它必须改发送/回显核心流程，应暂停该增强，按 D023 重新评估，不以本提案原则接受作为重构授权。

**启动边界与降级必须如实显示：**页面进入至 marker 确认之间属于“正在建立提醒”，该期间开始前已经提交的记录按历史加载，不承诺从路由点击的毫秒起捕获一切变化。marker 成立后，即使首屏未加载完，相关事件也必须提示。若要求路由切换瞬间的严格覆盖，还需扩展带服务器边界的数据订阅协议，不能假称现有代码已具备。断网进入一个新 scope 时同样显示尚未建立；已建立的 scope 断网则等待恢复后补提醒。

若选纯前端备选：完整首次快照建立 ID 基线后才开始差分，保存发送响应的 clientMsgId 并缓冲响应前事件。它仍有初始化窗口和请求结果不确定时的误报风险；不能用固定延时、文本匹配或屏蔽所有服务账号消息掩盖限制。推荐先选协议补充路径，避免把这些问题留给用户猜。

## 状态机与接口草图

以下仅表达职责，具体命名可在实施时调整；所有调用都携带同一 lease，过期 lease 无效。

```ts
type PageScope = { pageType: string; entityId: string; contextKey: string }; // 注册表白名单
type Lease = { scope: PageScope; sessionEpoch: number; generation: number };
type Update = { key: string; seq: number; targetId: string; version: string };
// 列表范围也是 target；version 只确认对应版本，不是整页 clearAll。

// 单一页面负责人注册；嵌套组件只通过 lease 提交证据。
activate(scope: PageScope, baseTitle: string): Lease;
establish(lease: Lease, startSeq: number): void;
observe(lease: Lease, update: Update): void;
confirmPresented(
  lease: Lease, targets: { key: string; version: string }[], interactionToken: string,
): void;
deactivate(lease: Lease): void;
```

```text
inactive → establishing → quiet
                    └── 合格事件 → pending（可先于正文加载成功）
quiet + 合格事件 → pending
pending + 有效操作及对应内容呈现 → 移除该批项；集合空才回 quiet
任意状态 + scope/session 结束 → inactive，释放资源
focus / visibility 变化只重算展示，不自动确认
```

建议由一个 `PageAttentionProvider` 持有当前 scope/session/generation、候选去重与状态、focus/visibility、浏览器标题/favicon，以及相关真实操作确认。它不认识 account/run/group 的字段、不请求业务数据、不管理分页或重试策略。页面适配器定义 event→业务变化、相关性、目标/版本、快照投影和呈现证据；路由层决定唯一 owner，Timeline/卡片/步骤组件提供对应证据。组件不得各自写 document.title 或 favicon。

新增页面通常只需：注册 scope/context；映射少量持久事件或成功快照差分；给实际渲染区域标记目标/版本并上报操作；补隔离/确认测试。具备可靠事件与稳定目标 ID 的简单页边际约 2–4 小时；缺事件或结果过期语义的页面会更高。不是零成本或自动全站接入，不建立通用查询语言、插件框架、跨页消息仓库。范围级候选与记录级候选可用同一状态机，不需要第二套全局系统。

基础标题和提醒前缀从状态派生，不读取已有标题反复拼接。管理器进入时记录原始图标节点属性；自己增加的节点在销毁时移除，原有节点则恢复。统一处理路由更换、登录退出、错误边界卸载、React 开发模式重复挂载；旧 lease 的 cleanup 不能覆盖新 owner 的标题。focus/blur/visibility、交互监听和 observer 都由明确生命周期注销。

favicon 建议使用本地静态正常/红点两份图标，复用当前品牌 K 的视觉，不引入图像生成、远端图标服务或 canvas 定时重绘。不显示精确数量，不以颜色作为唯一信号。页内入口支持键盘，状态文案可用 `aria-live="polite"`，只在无提示→有提示时播报，避免每条消息打断。

## 边界与未验证限制

- **前台持续更新：**同一轮多个更新合并为一个入口；已有提示不闪动。用户停在旧消息时保持原位置；晚到消息可能插入历史位置，“查看”要按待关注 ID 定位，不能只滚到底。
- **多标签页：**A 标签关注群 A，B 标签关注群 B；同群的两个标签分别确认，互不清除。不用 localStorage/BroadcastChannel 做隐式全局已读。
- **内容缺失或身份归并：**合格事件对应内容暂未取到时保留待同步状态；快照成功但 ID 已归并时按别名找最终行。找不到时提供重新同步，不自动当作已看过。
- **权限/实体失效：**明确 401、退出成功、确定 403/404 后终止该 scope 并展示现有错误；网络失败不能伪装成离开页面或确认成功。退出请求失败且仍登录则不提前清空。
- **重放缺口：**当前源码没有事件保留窗口/缺口协议。方案依赖所需事件仍可重放；若以后裁剪或重置事件流，须增加 reset/gap 信号并显示“同步范围待确认”，不能把任意快照差异报成新消息。旧缺字段事件也不具备新契约保证。
- **资源有界：**只保留活动 scope，合并 seq/消息别名；极长会话若达到实现时确定的待关注上限，降为一个“更新较多，需重新同步查看”状态，不能静默丢项后自动清空。首版不提供准确未读数。
- **浏览器限制：**标题/favicon 是页面可执行时的标签提示，不能保证用户已注意、浏览器被冻结时的实时性或窗口被遮住时一定看见。恢复执行后应重连补齐；favicon 动态刷新、固定标签及不同主题的实际显示仍待 Chrome/Edge/Safari 验证。本次未打开或自动操作用户验收页。

## 协议缺口、兼容性与基线核对

本轮已只读核对原始第 2.1/2.2/2.3、A0–A5、B1/B3/B4 与第 4 节，以及 main 工程规则 D022/D023。标题/favicon 提醒和页面关注确认属于用户新增要求；原文未要求它们，也没有明确禁止，不能把“未提到”写成冲突。原文明确不要求的 i18n/主题切换/响应式未纳入。以下是本方案各接入点的核对结果，不表示原系统所有功能已验收。

| 补充候选 | 当前缺口与兼容约束 | 对核心的影响判断 |
|---|---|---|
| 起点 marker | 保留原 auth 请求/成功帧、`{seq,type,payload}` 与 sinceSeq 重放；marker 只响应新客户端显式请求，不向旧客户端无条件推非事件帧，不推进业务消费游标 | 局部 WS 控制分支；新增控制帧属于原文未覆盖的补充契约，仍待具体评审。旧客户端与新客户端连旧服务都需覆盖。旧服务不支持时明确降级，不能直接假定提醒已建立 |
| message 分类与发送关联 | 保留原 message 必备字段、deliveryStatus、isOwn、GET 分页、POST 原必填字段和 202/clientMsgId 响应；新增字段可选，原无 clientMsgId 请求仍由服务生成 | 前端/API 局部扩展；原文 2.1 网关不按 clientMsgId 去重，不能借关联 ID 新增自动重发。回显无法确证仍保留限制 |
| 账号/群字段变化 | account_status_changed 的 from/to 只代表真实合法转移；同状态限流时间变化另用 account_changed。group_changed 可加 changedFields，重核决定具体变化，no-op PATCH 不报业务更新 | 在现有字段写入处补观察信息；不改变 A1 CAS、终态联动、群状态枚举和成员权限 |
| Agent 步骤 | agent_run 原字段/公开 status 不变；建议新 agent_step_changed 带 runId/groupId/ordinal/changedFields，GET steps 可选增 ordinal；已有 ordinal 可复用，无需新表 | 步骤插入、结果/错误/审计字段更新的提交点补事件；不改变工具协议、步骤计数、12步/60秒、审计重试或副作用时序 |
| 序列步骤/定义 | sequence_run 的 currentStepIndex 继续表示当前步骤；变化步骤另用 stepIndex，不重新解释旧字段。模板创建新增 sequence_definition_changed；步骤补事件只在展示字段实值变化时发 | 复用持久 events；不改变 B1 排期、skipped 语义、变量来源、互斥与恢复接管。accepted 每次扫描写同值不能反复发提醒事件 |
| 当前 job | 若纳入同等重放保证，新增 job_changed，含 jobId、关联 groupId（可空）、状态/变化分类 | 只观察现有任务提交；不改创建/退群工作流及恢复策略。不接入全局任务收件箱 |

**步骤事件事实：**[agent.ts](../apps/server/src/modules/automation/agent.ts) 的 notify 主要在创建/终态；普通 step 插入、protocolError 和普通 completeStep 没有逐步 notify。[tool-execution.ts](../apps/server/src/modules/automation/tool-execution.ts) 的 auditVerdict/部分结果更新也有独立写入点。[sequences.ts](../apps/server/src/modules/automation/sequences.ts) 的 notify 覆盖启动、progress 和停止，但 accepted、关联 clientMsgId 与 rebaseExpired 的排期改动不能仅靠 currentStepIndex 识别。必须审查这些写入点，不能只给现有 notify 加一个字段就声称全部覆盖。

**首屏与跨实体后果也需补足定位：**要覆盖 marker 成立后、首屏尚无比较基线的变化，新事件的 changedFields 必须来自提交时真实前后差异，而不是照抄 PATCH 请求键；旧事件只有 groupId 时只做待核对，不能凭首次快照猜新旧。account_terminal 当前只带 accountId；建议在原成员删除事务中保留受影响 groupId，并补 group_changed，序列步骤被跳过则按返回的 runId/index 补步骤事件，避免初次快照已删成员后失去关联证据。这些只是同事务观察信息，不改变删除/取消/跳过行为。

新增可显示变化事件应与对应领域状态在同一现有事务提交，复用 [db.emit](../apps/server/src/core/db.ts) 的提交顺序机制；没有事务的模板创建/观察写点需小范围事务包裹。不得在业务事务中等待浏览器、向通知系统发网络请求或追加新的执行重试；通知层不发消息、不调审计、不推进步骤。增加事件会增加现有全局 revision 驱动的重核次数，应合并实际变化/同事务事件并测负载，不能趁机把整个数据层改成新缓存框架。

初始化、首次历史、marker 前窗口、重连同 scope 保留起点、乱序去重、发送响应晚于 WS、身份归并和加载失败不能确认等上一版规则全部保留。新页面只看最终状态差分可漏掉轮询间的短暂变化；若要求可靠捕获，必须有持久事件。原先对“Agent 详情再加 3–5 小时”的粗估未覆盖逐步事件补点，本轮据源码修正为 4–7 小时，并增加跨页验证预算。

本标签手动发送排除继续只按精确 clientMsgId。账号操作、群资料保存等同步动作可以复用已有成功响应和已呈现结果，避免重复提示，但没有操作关联证据时不按“最近点过按钮”吞事件；用户发起的建群、Agent 或序列在后台完成/失败仍值得提醒，不因是用户发起就永久屏蔽。这个处理不放宽“未呈现不能确认”。

同一实体连续变化推荐合并到最新版本，但保留“期间发生变化”的证据；若要求逐次中间态都可阅读，需增加变化历史展示/存储，这是不同规模，应重新评估。消息依然按逻辑消息身份逐条保留，不用状态合并规则吞掉不同消息。

**边界条件：**若严格查询相关性需要新增服务端查询订阅、任意规模 3 秒补齐需要重写推送/快照、回显归并需要改发送核心，或逐次中间态需要新历史模型，不能再归为本次局部适配。先按 D023 给影响评估；若还与原文明确条款/排除范围冲突，则依 D022 提醒并取得规定的两次分开确认。当前没有把这些备选视为已授权，也不要求用户为普通文档评估重复确认。

**全部覆盖合计 38–66 小时（约 5–9 个 8 小时单人工日）。**原群消息路径的 15–25 小时仍对应前两项，不能沿用它承诺全部页面。结构是中等复杂度的横向接入；若“中等”同时要求两三天全部完工，当前证据不支持。

推荐批次：①共享核心+群消息 15–25 小时；②账号、群目录、群详情其他区和 Agent 列表新增 9–17 小时；③Agent 详情、序列、当前 job 及完整跨页回归新增 14–24 小时。每批单独验证交付，复用同一核心，避免一次跨所有写入点集成。批次不是自动的上线或合并授权；是否首版全部覆盖仍待用户决定。

真正拉高成本的是事件准确性、旧/新契约兼容、身份不确定窗口、查询范围过期和“已成功呈现”的确认边界，标题与红点本身只占小部分。若省掉这些，只做每次 revision 亮红点会误报，不能称满足用户所选规则。

**原始基础要求优先：**A4 的消息分页不重不漏、A5 的审计/副作用/步骤可见、B1 的排期恢复、B4 的重连后 3 秒呈现均不能为了提醒降级。当前 main 功能总表仍记录未知投递/建群/工具恢复的协议限制、部分基础验证缺口，且任意规模 3 秒尚未证明；提醒不能被写成这些问题已经解决。工程截止与整体验收预算也存在，全部接入可能挤占基础验收，应先明确时间取舍，不能用乐观并行估计掩盖。

## 不改变原流程的验证方法（实施后，隔离环境）

1. **静态契约与旧消费者：**原必备请求/响应字段与全部公开状态枚举逐项比对；旧 `/api/groups` 数组与 Sequences 保留；viewer 写入仍 403；旧 WS 客户端不发 marker 也能消费原帧。新增字段缺失时不能崩溃或伪造精确提醒。
2. **业务副作用对比：**在独立测试库/模拟器复跑相关 S1–S8 与既有聚焦测试，核对发送次数、clientMsgId、审计调用/工具次数、run/step 状态、排期与取消结果一致；新增的只是持久观察事件和 UI 状态。测试事件必须对应已提交状态，回滚不留下虚假提醒。
3. **可显示变化覆盖：**普通步骤、协议错误步、审计结论、序列 accepted/终态/重排期、同状态限流续期、任务失败分别触发；同值重写、轮询、心跳均不增加候选。相邻变化合并到可呈现的最新版本，不丢不同消息。
4. **恢复与提交证据：**初始重放、断流/重连、失败重试、旧快照晚到、seq 重复、POST 慢响应逐项验证；refresh Promise 完成但 data 未成功更新不能确认。仅局部 DB 测试证明事务；只有浏览器实测才能记录呈现时间，不能以新提醒放宽 B4。
5. **分页与跨页：**在另一线程完成并交付分页契约后再做接入验证，不操作其进行中工作区；旧 cursor 禁止续接、结果过期不被清红点解除、选择切换不串实体、标题只有一个 owner。全部使用隔离环境，不能对当前演示库注入数据/故障。
