## 容量接入与证据边界

容量接入实现与开发自测已完成，具体启动命令、实例归属、能力集合、历史证据与限制见 [容量接入交接](qa-capacity-control-handoff.md)。采用独立的本机控制器与显式测试 SUT 入口，正常服务入口不加载控制器。控制占用同一个 SUT `Database` 的真实准入槽；不强制返回容量错误，也不补写产品业务状态。QA 仍须配置并实际验证接入，不能仅由开发检查通过认定 CAP-001 至 CAP-010 通过。

已向 QA 反馈并获其确认的边界如下：

| 条目               | 已识别事实                                                                                                                                            | 处理原则                                                                                                                                     |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| CAP-003 活动计时   | 持久计量值与终态观察存在采样、提交间隔；开发 DC06 一次实际记录为 `[60007,60022]`，持久值 60007ms，外部单调计时区间约 `[59996.85,60019.20]`            | 不将值截断为 `[60000,60000]`。该次计量下界已超 60000ms，属于需要保留的产品时限问题，不能一律称为跨界证据不足。QA 尚未独立执行该场景          |
| CAP-009 拒绝后崩溃 | 开发 DC04 已复现：先保存 `executing`，真实容量拒绝后、`ready` 回写前硬杀，恢复公开 run 仍为 running 并带 recoveryNote；零 kick，一次 audit、一次 turn | 控制器只保持精确窗口，不替产品写 `ready` 或补持久证明。该次暂停不满足本场景的自动续跑预期；开发复现与 QA 实测分别记录，不登记为 QA 实测 FAIL |
| 归属与回收         | QA guardian PID 不一定等于应用 PID；旧用例可能先杀进程组再清理租约                                                                                    | 交叉核对实际应用、进程组、API 监听、启动提交与所有者；独立控制器保留租约历史，TTL 有界，不允许旧租约影响复用端口的新实例                     |

本批接入验证前提是专属 PostgreSQL 健康、控制进程正常响应；QA 已确认当前 CAP-001 至 CAP-010 未加入 PostgreSQL 永久挂起故障。如果连接获取或 advisory SQL 永久无响应，当前基础数据库接口无法取消该等待，未证明实际槽位在 120 秒内归还；控制器应保持不可用/未释放证据，不能伪报 released。进程确已死亡时的回收另有核验，不以 `ps` 查询失败代替死亡证明。

最终集成版本的 DC04 再次复现相同暂停；DC06 再次记录 `[60004,60108]ms`，持久值 60004ms，外部公开观察区间约 `[59995.82,60010.32]ms`。两轮原始数值分别保留，没有用后一次结果覆盖前一次结果，也未调整业务阈值。这两条作为**未修复的开发复现问题**交给 QA，不是本批测试控制器内暗中修复的业务功能。
