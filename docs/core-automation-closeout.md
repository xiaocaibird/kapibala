## CG05：kick 的未决操作和重入

**原保证与缺口。** A5.8 L264 要求任意中断后同 run 正常继续，已经对外产生效果的工具不能重复、不能记失败。2.1 L52–55 的 kick 没有稳定操作 ID 或按操作查询结果；成员 GET 给当前状态。持久 `executing` 可能对应“意图写入后尚未请求”或“移除已发生、响应/本地提交丢失”。目标目前仍在群中又有两种可能：根本未移除，或者移除后重新加入；目前不在群中也不能单凭成员状态把操作关联到某次未收到明确响应的请求。

**现状及影响。** `tool-execution.ts:335` 对遗留 executing kick 保留意图、暂停自动重放；`messages.ts:549` 对明确 504 等待收敛后查询成员，目标仍存在时仍报告不确定，不补踢。已有明确 200 后重入的投影修复属于另一个“已知操作成功”窗口，不能解决响应未保存。预算在正在执行的 kick 中耗尽时，可结束 run 为 failed/wall_clock，但工具意图继续 executing、记录未知说明；不能把 run 的预算终止解释为 kick 失败。此策略保护“不重复制造副作用”，代价是部分 run 无法自动正常结束。

**原协议内可做什么。** 继续保存 intent、恢复说明与 inconsistency；明确收到的结果正常提交。原文已有 504 可判定路径保留，不重做已知结果、不以“再查一次当前成员”宣称所有未决操作可判定。本次静态复核和已有专项没有发现可用普通本地修复消除的具体 bug，未新增恢复按钮或重试路径。

**真正闭合所需机制。** 网关需要接收并持久去重稳定 operationId，返回该次操作的原始结果；或提供同等强度的按操作结果查询，并明确“未执行/已执行/仍处理中”和记录保留期。特别要保证目标重新加入后，重取旧操作结果不会再移除这次新成员关系。单纯客户端生成一个 ID、只加数据库唯一键或重复传同一参数不足。

**兼容成本/待决。** 这是 2.1 外部协议能力增强，需网关、适配层/意图字段、模拟服务和响应丢失/重入回归共同调整；现有操作者 API 可以保持不变，但不能假定现有外部实现理解新增字段。若暂不具备此机制，最小现状仍为保守暂停。接受此偏差只能依据 D022 单独确认带限制交付，不能将 A5.8 强保证标成满足。本轮不作接受决定。

## CG06：Agent 原轮响应丢失

**原保证与缺口。** 2.2 L89–104 仅说明以 runId 维护会话，同一个 runId 不是同一轮的幂等身份；A5.2–3 要保留每轮步骤和完整历史，A5.8 要从中断处继续。原协议没有 turnId、读取某轮响应或会话回滚接口。`agent.ts:403` 先写 inflight_turn，后发送请求；恢复看到该标记时在 `agent.ts:306` 暂停。如果原服务已推进会话但本地未保存响应，重复旧历史不能证明返回的是原轮同一结果；直接把它当成新轮继续也不能重建丢失轮次的原始响应与步骤。

**现状及影响。** 保留同 runId、已有历史、inflight_turn 与 recoveryNote，推 inconsistency，不虚造一条成功或失败的旧轮。这不是“所有重启均正常结束”。普通可观察的 turn 超时按 TURN_TIMEOUT 追加协议错误并可继续，已保存合法 final/工具结果可以恢复；这两种已知边界不等同于进程消失时尚未落库的响应窗口。响应丢失本身也不证明工具已经执行：Agent 只返回工具建议，外部工具效果由后端另行调用，应分别核对工具 intent。

**真正闭合所需机制与成本。** Agent 服务需要稳定 turnId，并对重复 turnId 返回原始响应，或可靠查询该轮处理状态/响应；还要绑定请求历史或版本、防止不同请求复用同一个轮次 ID，规定记录保留期及“处理尚未完成”的含义。后端先持久该身份，再派发、取回结果、原子提交历史；中断恢复依据确定结果继续。需共同改动 2.2 服务、后端适配/持久状态、模拟器及原轮响应丢失/接管回归。仅要求模型温度为零、同 runId 或同 prompt 不能给出这个保证。当前协议下最小保守策略仍是暂停；若接受无法自动完成的偏差，须单独依 D022 决定，本记录不代为闭合。

## CG08：计量语义与时钟方案影响

**正常路径与本轮边界。** `activity-clock.ts:21` 每 500ms 触发采样，统一给 running 且无 recoveryNote 的运行累计时间，包括等待执行槽的运行；`agent.ts:315` 同时保留本次执行的本地截止时间。持锁的同一 PostgreSQL 连接写时间，接管先经过初始化事务栅栏，再重设采样起点；正常 close 补最后一次采样。已有多实例/实际停机/初始化屏障回归和本次正常采样、实际恢复检查没有复现新的普通在线计量或停机误扣 bug，本次不改算法。

**无法证明的部分及实测。** 采样 S 后到硬终止 K 之间的在线尾段没有提交，重启 R 时只有 S 的累计值。K 早或晚的两个执行历史可以留下相同数据库状态；只用本地持久状态不能反推出准确 K。本次在测试进程里阻塞事件循环后 SIGKILL，直接观察到 1177ms 尾段未记账，超过一次 500ms 定时周期；停机 705ms 没有被补算。该实验使用生产 ActivityClock 类与真实 PG，不是整套 Agent 业务进程的系统崩溃证明，也不把一次 1177ms 测量当成上界。

当前执行仍用本地 deadline，在普通进程持续运行时不因心跳采样慢而重新获得 60 秒。硬终止/时钟失联后接管会排除未知尾段；重复中断可以累计少计。事件循环延迟、数据库阻塞或失联使间隔扩大，因此“500ms 定时器”不提供任意崩溃的严格误差上限。

| 候选处理 | 能证明什么 | 兼容成本及不足 |
|---|---|---|
| 保留现有采样、截止时间与保守接管 | 现有正常活动计量、样本不双计、停机排除、未知尾段明确受限 | 最小现状，无新产品/协议；不能标原保证完全满足，接受误差仍需 D022 单独决定 |
| 缩短采样周期或增加检查点 | 在相同健康条件下减小常见未持久化尾段 | 更多 DB 写入/争用；不能消除硬终止与最后提交之间的窗口，也不给任意阻塞的硬上界，不作为本轮必要修复 |
| 预扣未来一段预算/用租约到期推算 | 可选择保守限制总可用预算 | 可能把实际停机尾段算作在线，与“停机不计”存在偏差；不能同时声称两项绝对保证，需先明确可接受语义 |
| 引入独立、持久的进程在线区间/预算仲裁机制 | 在明确的失联、时钟与故障模型及精度约定下，才可评估严格上界 | 需定义何为“在线”、进程暂停/网络分区/DB故障时谁计费和谁阻止执行；外部观察本身仍有检测延迟，不能泛称增加一个心跳就变得精确。涉及持久计时、生命周期及截止执行方案，按 D023 先评审核心影响，再决定实施 |

真正要把“任意硬停机仍精确累计在线 60 秒”闭合，须先给出能可靠区分在线结束与停机的证据源、故障模型和计量精度，再用跨进程异常验证该方案；若这些条件不能提供，就应保留未满足状态。新 10/15 秒超时证据不消除这项恢复计量限制。本轮没有擅自将允许误差写成需求，也没有通过预扣离线时间伪装闭合。
