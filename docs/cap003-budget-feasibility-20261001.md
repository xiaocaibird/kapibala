# CAP003 活动预算：晚派发修复与严格上限边界

后续独立 QA 已在固定 `86ad4e7` 实测连续运行活动区间 `[60010,60112]ms`，保留 FAIL，具体证据及工程结论见[时间边界失败复核](qa-timing-boundary-followup-20261001.md)。下文各次开发测量保持原版本和原数值，不以此新证据覆盖历史。

2026-10-01，基线 `b86b0ad`，模型派发修复 `9c1de53`，审计派发修复 `9c98c51`。**CAP003 的真实活动 60000ms 上限仍未闭合，不能标 PASS。** 本批只修已复现的模型/审计晚派发，没有修改独立 QA、既有断言、60000ms 预算、计量值或容差，也没有引入提前的 `wall_clock` 结论。

## 原因与修复范围

`ActivityClock` 的 500ms 采样决定持久账本更新频率，但执行中的 run 并非只看采样值：`AgentModule.remaining()` 使用 `activity_updated_at + 60000 - active_ms` 建立本地 deadline，包含尚未采样的时间。模型请求的超时和容量等待都已受这个剩余时间约束。因此，DC06 的几毫秒越界不能简单归因于“等到下一次 500ms 采样才检查预算”。

找到并修复的确定性问题位于 `AgentModule.turn()`：代码先取得剩余预算，再等待 `inflight_turn=true` 的 SQL，之后仍按旧的剩余预算发出 HTTP 请求。真实数据库写入阻塞能消耗全部剩余预算，旧代码仍会派发；未完全耗尽时也会把数据库等待时间额外赠给远端请求。

修复在 intent SQL 和请求正文序列化完成后重新检查原 deadline，并以此时剩余时间创建 HTTP timeout。预算已耗尽则不调用 `fetch`，按既有终态流程结束。没有延长预算、预扣未来活动或改变 clock 的 owner/接管规则。

`AgentTools.audit()` 存在相同顺序问题：审计尝试的持久写入可能耗尽预算。对应修复同样在写入和序列化之后重查剩余时间，未发出审计请求时不会保存任何审计结论；原来已经落库的 attempt 保持现有审计尝试定义。

开发专用反例用 PostgreSQL trigger 对真实 intent UPDATE 执行 `pg_sleep(0.35)`，在仅余 200ms 的短预算夹具中复现该调度竞态。修前模型服务收到 **1** 次请求，真实持久活动 **60205ms**；修后收到 **0** 次请求、无步骤/审计/网关请求，真实持久活动仍为 **60173ms**。这个短预算夹具只证明晚派发修复，绝不冒充真实一分钟上限测试。原始[修前失败](evidence/cap003-dispatch-before.log)和[修后日志](evidence/cap003-dispatch-after.log)均保留。

独立审计反例同样阻塞真实 `agent_steps` UPDATE：修前收到 **1** 次审计请求、持久活动 **60205ms**；修后 **0** 次审计请求、持久活动 **60194ms**，没有网关请求或审计结论。原始[审计修前失败](evidence/cap003-audit-dispatch-before.log)和[审计修后日志](evidence/cap003-audit-dispatch-after.log)保留；未截去数据库阻塞造成的真实活动。

## 为什么真实上限仍未保证

当前活动定义包含从创建到真实终止判定的在线编排时间。到达 deadline 后，Node 定时器只能在事件循环取得执行机会时触发；随后还有远端取消处理、后置记账、终态事务和提交。`finish()` 的检查点只在终态事务之前，不能消除检查点之后仍真实存在的活动尾段。数据库锁等待和事件循环阻塞也没有可证明的最坏耗时界。

若坚持“活动真实上界不超过 60000ms”，同时不得在真实耗尽前以 `wall_clock` 结束，则当前通用 Node/PostgreSQL 执行模型无法给出零正尾差保证。另起更精细的定时器、把采样频率提高或提前安排取消都不能凭配置值建立物理最坏界。把时间截成 60000、把 terminal 提交等待从见证中擅自扣掉、将预留时间伪装成已耗尽，均不构成修复。

等待执行槽的 run 仍按既有共享 clock 计费；取得执行权后的预算检查阻止过期 run 再发起新阶段。四个执行槽、调度 tick、数据库等待也意味着“持久预算已耗尽”和“公开终态提交”之间仍可能有延迟。本批没有添加绕过所有权或容量限制的独立终态写入器。

## 可选后续路径及影响

| 路径                       | 实际含义与影响                                                                                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保留当前严格契约           | CAP003 保持未满足；继续保存真实观察，不据本批开发测试通过数改判。此路径无需改变业务要求。                                                                   |
| 明确采用 deadline 授权语义 | 到达原 deadline 后禁止新派发，并尽快取消在途本地等待；终态提交可以晚于 deadline，全部真实耗时仍报告。需要产品负责人和 QA 明确修改业务结束边界；本批未采用。 |
| 要求严格物理完成界         | 必须先定义可验证的活动边界、时钟误差，以及调度、取消、数据库提交和远端执行的最坏时间界。当前运行时和远端协议没有提供这些保证，不能仅靠本地代码宣称可达成。  |

本批不会把“允许约几毫秒误差”作为默认修复。硬杀的 D040 边界同样保留：本次回归仍观察到 **1169ms** 未落库在线尾段；停机 **710ms**，接管即时补计 **2ms**。不能把 500ms 采样频率写成任意崩溃下的误差上限。
