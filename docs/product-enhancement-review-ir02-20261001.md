**一、建议调整现有提案的组织和优先级**

现有提案准确保留了需求来源和历史边界，但“原始需求之外”与“正式产品可以暂缓”是两个不同判断。例如，下一条草稿被清空、写入结果未知后只能再次点击、序列开始后无法限定范围停止，都可能影响日常使用，不能仅因原始需求没有明确要求而长期放在普通可选增强中。

本报告采用以下优先级：

| 优先级 | 含义 |
|---|---|
| **P1：高优先** | 涉及误发、不可撤回效果、输入丢失、结果误判，或关键流程缺少可执行的兜底；建议在正式交付前解决或明确产品边界 |
| **P2：中优先** | 明显改善常见流程、减少理解和操作成本，可以随后集中补齐 |
| **P3：低优先** | 完整平台能力、复杂配置或缺少使用证据的扩展，适合后置 |

这是产品增强的排序，不是对整个项目作出的上线通过或不通过结论。

建议保留 PI 编号供关联，但重新按用户流程组织：

|---|---|

| PI-01-c、PI-06-b | 从确认文案扩为“操作影响与业务边界”，相关高影响场景为 P1 |

| PI-18-c、PI-20-b/c | 保留读取失败、陈旧数据和身份连续性的产品要求；跨标签风险先专项复验 |

**二、高优先补充与调整**

**1. 提交成功只能清理本次提交的输入，不能清掉后来编辑的草稿。关联 PI-03-b、PI-08。**

当前人工发送成功后无条件清空输入框，而提交期间输入仍可编辑。因此，慢响应可能清掉用户后来输入的下一条消息。这条路径由源码确认，实际浏览器场景本轮未复现。[发送处理](/Users/zcm/Desktop/kapibala/apps/web/src/components/Timeline.tsx:128)、[输入区域](/Users/zcm/Desktop/kapibala/apps/web/src/components/Timeline.tsx:246)。

序列创建弹窗也仍可通过关闭按钮或 Escape 离开；表单内部按钮的 busy 限制没有覆盖弹窗的所有关闭方式。[序列创建弹窗](/Users/zcm/Desktop/kapibala/apps/web/src/pages/Sequences.tsx:583)。

最小需求是：

- 提交成功仅清理本次提交对应的输入；也可以明确采用提交期间锁定输入的策略。
- 明确失败时保留输入。
- 弹窗所有关闭方式遵循同一套提交中、未保存保护规则。
- 离开页面不能让用户误以为后台操作同时取消。

验收应覆盖：慢成功期间编辑下一条、明确失败、提交中关闭弹窗，以及完成预检前后离页。无需同时建设跨登录、跨设备的持久草稿系统。

**2. 序列预检必须确认实际目标和执行范围，避免“内容正确、目标错误”。扩充 PI-14-b。**

当前预检保存原目标，实际启动也使用该目标，这一做法避免了启动时读取另一份参数。但预检期间群和模板选择仍可变化，确认弹窗又没有展示目标群、模板、角色和延迟。已选对象失效时，页面还会回退到列表首项。[选择处理](/Users/zcm/Desktop/kapibala/apps/web/src/pages/Sequences.tsx:94)、[预检与启动](/Users/zcm/Desktop/kapibala/apps/web/src/pages/Sequences.tsx:132)、[确认弹窗](/Users/zcm/Desktop/kapibala/apps/web/src/pages/Sequences.tsx:398)。

最小需求是：

- 确认页展示群名称及稳定 ID、模板名称、最终文本、各步角色和相对等待规则。
- 预检期间固定选择上下文，或使变化后的预检明确失效。
- 用户已经选择的群或模板失效后，要求重新确认，不能静默换成另一项。
- 切换群或模板时，明确变量草稿是保留、清空还是分别保存。
- 明确“变量预检通过”不等于所有步骤一定能够发送。

角色可用性快照可以作为补充，但必须说明会变化。没有匹配角色时仍应遵循既有跳过规则，不应借此一律阻止启动。

验收应覆盖：填完 A 群参数后切到 B 群、切换模板、预检期间改变选择、原目标失效，以及预检通过后执行账号状态变化。

**3. 写入结果未知时，产品需要提供核对原操作的路径。调整 PI-09-b/c。**

浏览器没有收到成功响应，不代表服务端没有受理。对于发消息、建群、退群和启动序列，笼统提示“失败，请重试”可能诱导用户再次产生外部效果。

当前人工发送每次提交生成新的 `clientMsgId`；已有同 ID 冲突检查也不等于重复请求返回原结果的能力。[发送 ID 生成](/Users/zcm/Desktop/kapibala/apps/web/src/components/Timeline.tsx:131)、[提案现有边界](/Users/zcm/Desktop/kapibala/docs/product-enhancement-proposal.md:97)。

建议先明确产品行为：

- 区分明确拒绝与无法确认是否受理。
- 结果未知时保留目标、正文和可用的关联 ID。
- “核对结果”读取原消息、原任务或原运行，不通过再次提交制造新操作。
- 同一次操作的再次尝试与用户主动发起的新操作应可区分。
- 无法核实时，说明已知事实、未知范围及实际可用的人工处理出口。

不能把消息 `unknown`、请求断网或普通查询 404直接解释为“没有执行”。也不应提供没有事实依据的强制重发、强制成功或一键恢复。

验收重点是“服务端已受理、浏览器响应丢失”：用户仍能核对原操作，并且不会被引导重复执行。

**4. 运行状态与实际业务效果应分开呈现。合并 PI-04-b、PI-10-b、PI-12-b、PI-16-b。**

当前存在几种不同的业务含义：

| 页面状态或结果 | 需要解释的事实 |
|---|---|
| 消息已受理 | 尚未证明最终发送成功 |
| Agent 正常结束 | 不保证所有消息最终送达，也不保证本次一定发过消息 |
| Agent 审计阻塞 | 当前受阻调用未执行；此前步骤可能已经产生效果 |
| Agent 已取消 | 后续编排结束，不等于已发消息或已完成移除被撤销 |
| 任务已有错误 | 可能仍在继续处理剩余步骤 |
| 序列步骤已处理 | 包含发送、跳过和失败，不能解释成全部发送成功 |

后端任务已经返回 `processing`，前端任务 schema 没有保留它；前端也将所有非 `running` 状态触发为完成回调。因此，“发现失败但仍在处理”和“已经结束”没有充分区分。[任务查询](/Users/zcm/Desktop/kapibala/apps/server/src/modules/gateway/jobs.ts:121)、[任务组件](/Users/zcm/Desktop/kapibala/apps/web/src/components/JobProgress.tsx:23)。

Agent 的“副作用未执行”提示也应限定到当前受阻调用，避免被理解为整次运行没有任何效果。[当前受阻提示](/Users/zcm/Desktop/kapibala/apps/web/src/pages/AgentRuns.tsx:160)。

最小需求是：在保留现有状态契约的基础上，分别展示处理是否继续、已确认效果、尚未确认效果和允许的下一步。工具当时返回的 `accepted` 与消息现在的 `sent/failed/unknown`应并列保留，不能互相覆盖。

验收至少覆盖四类：前一步已发送、后一步审计阻塞；工具受理后运行结束、消息随后失败；只生成结束摘要没有对外发送；退群部分失败但剩余步骤仍在处理。

**5. 新增“停止指定序列的后续发送”，作为业务止损能力。P1。**

当前序列提供创建、预检、启动和查询，没有操作者停止该次运行的入口。关闭 Agent 只影响 Agent；断开账号会影响其他群，也不能被当作取消排队消息的替代手段。[序列接口](/Users/zcm/Desktop/kapibala/apps/server/src/modules/automation/sequences.ts:145)、[Agent 关闭处理](/Users/zcm/Desktop/kapibala/apps/server/src/modules/gateway/index.ts:218)。

当活动取消、目标选错或变量错误在启动后才被发现，产品缺少范围明确的止损动作。这不是简单的提示问题。

建议最小范围为：

- 管理员可以停止指定序列尚未开始的后续步骤。
- 明确已入队但尚未派发的消息如何处置。
- 已发送、已取消、在途或结果未知分别呈现。
- 操作者主动停止与群不可写导致停止分别保留原因。
- 停止不承诺撤回，也不影响其他群。

完整暂停、修改后继续、重新排期可以后置。

验收应覆盖首步已发送、第二步限流排队、第三步尚未开始时停止，确保后续行为与页面解释一致。

**6. 退群需要明确“退出处理中”的业务边界。扩充 PI-06-b，P1。**

当前退群受理只创建任务，群仍可能保持 `active`；全部成功后才写入 `left`。因此，退群期间仍可能允许人工发送、新序列或自动执行。[退群受理](/Users/zcm/Desktop/kapibala/apps/server/src/modules/gateway/jobs.ts:83)、[退群完成处理](/Users/zcm/Desktop/kapibala/apps/server/src/modules/gateway/jobs.ts:507)。

原始需求规定了退出顺序和部分失败处理，但没有完整规定这段期间其他业务动作的关系。这应作为新增规则明确，不能仅归为确认文案。

建议：

- 展示退出处理中及原任务入口。
- 建议退出受理后禁止新的发送、序列和自动运行。
- 分别约定既有自动化、排队消息和在途请求如何处置。
- 部分失败后展示剩余服务账号、群主保留情况和允许的下一步。
- 再次操作应说明是在查看原任务，还是对剩余范围发起新任务。

确认页则应补齐目标群、退出范围和相关工作影响。当前已有“全部服务账号退群”确认，不需要重新提出“增加退群确认”本身；需要说明外部成员可能继续保留，以及退出服务账号不等于解散群。

验收应在存在 Agent、序列和排队消息的群中进行，检查退出全过程及部分失败后的动作是否互相矛盾。

**7. Agent 的开关、重新开启和自动移除，需要明确业务授权范围。扩充 PI-06、PI-12、PI-13。**

这一项建议分成三条规则，避免只用一个开关说明包办。

首先，**关闭 Agent 是停止后续编排的请求，不保证当前步骤立即结束**。当前实现会完成已准备的工具步骤后检查取消；已经入队的消息也不会因运行结束而自然撤销。[当前步骤处理](/Users/zcm/Desktop/kapibala/apps/server/src/modules/automation/agent.ts:445)。页面应区分“已请求停止”和“运行已结束”，同时明确 Agent 开关与序列相互独立。

其次，**关闭后重新开启，应明确哪些旧消息仍会处理**。至少区分关闭时尚未进入运行的消息、关闭期间的新消息，以及已属于取消或阻塞运行的触发消息。当前消息资格处理分布在事件入库和后台调度中，快速关开是否经过清理可能影响待处理项，这是源码推导，尚未复现。[待处理资格处理](/Users/zcm/Desktop/kapibala/apps/server/src/modules/automation/agent.ts:178)。产品应选择一致规则，不能笼统承诺重新开启会恢复原运行。

第三，**自动移除要定义“允许移除谁、依据什么”**。新 C2 提示已经要求具体管理理由，并要求不移除自有账号；这部分不能再报为没有策略。但提示中的约束与主后端不可绕过的目标保护规则是不同层次。[现有模型策略](/Users/zcm/Desktop/kapibala/apps/gemini-agent/src/app.ts:20)。

正式启用自动移除前，应明确：

- 哪些行为足以自动移除，成员口头要求移除别人是否构成依据。
- 哪些对象需要保护，尤其平台服务账号。
- 审计通过只代表满足内容审核规则，不能呈现为已证明目标应该被移除。

另外，人工发送目前不等于人工接管。最小交付可以先显示当前 Agent、序列仍在运行，并提供相关运行入口；无需自动把每次人工回复当成停止授权。

验收应覆盖慢步骤期间关闭、快速关开、关闭期间收到消息、人工回复与自动回复并行，以及请求移除自有账号等场景。

**8. 将导航来源和操作目标一致性纳入提案。目标一致性 P1，返回体验 P2。**

已有[导航与返回评估](/Users/zcm/Desktop/kapibala/docs/navigation-review-proposal.md:11)记录了实际反馈，但尚未实施，也没有进入增强提案的主要条目。

应纳入的最小要求：

- 从 Agent 列表进入详情，返回原列表并保留所选群；从群详情进入则返回原群。
- “返回来源”和“查看所属群”分别表达。
- 序列切换目标群后，地址、实际选择及刷新后的目标保持一致。
- 详情读取失败时仍能返回；已有重试入口应保留。
- 直接链接、来源失效及畸形地址有确定的站内兜底。
- 导航上下文不改变消息和运行提醒的实际对象范围。

其中，序列地址与实际操作群不一致比单纯返回不便更重要。已有目录状态保留约定应继续沿用，无需附带全站持久状态系统。

**9. 最小任务找回与异常关联，应作为兜底能力提前。合并 PI-05-c、PI-13-b、PI-17、PI-19-b。**

单建群任务刷新恢复已经存在。剩余问题是退群任务引用只在组件状态中，序列主要依赖当前活动运行和每群一个会话引用；离页、新会话或被下一次运行替换后，用户未必还能找到原记录。[退群任务引用](/Users/zcm/Desktop/kapibala/apps/web/src/pages/GroupDetail.tsx:41)、[序列运行引用](/Users/zcm/Desktop/kapibala/apps/web/src/pages/Sequences.tsx:83)。

建议首版只做：

- 从所属群找到当前任务和最近结束记录。
- 任务、运行详情具有稳定链接。
- 消息与产生它的人工操作、Agent 或序列建立可用关联。
- 隐藏提醒后仍能查回原对象；隐藏不代表问题解决。
- 没有定位到记录时，说明当前查询范围，不能直接宣称不存在历史。

异常下一步必须使用真实存在的能力：等待核查、读取原结果、停止后续动作或转人工处理。对于终态的 `blocked`运行，不应提示审计恢复后会自动继续，也不应显示没有实现的一键恢复承诺。

这不要求首版建设完整任务中心、异常中心或全历史检索平台。

**10. 读取失败、陈旧数据和身份变化应保持操作连续性。关联 PI-18-c、PI-20-b/c。**

最新 main 已修复若干读取错误和同页重试，剩余重点应收窄为：

- 旧数据仍可见但更新失败时，明确它不是已核对的最新状态。
- 查询失败与确实为空、没有可用账号分别呈现。
- 重新读取不会自动重新提交写入。
- 暂时连接异常与登录身份失效分别解释。
- 身份变化后，旧请求和旧草稿不能以新身份静默提交。

跨标签续期和身份一致性目前仍属风险推导，本轮没有专项复现。如果正式产品支持多标签同时操作，应将其列入验收条件；不应直接宣称已经发生越权。

跨登录保留草稿可以后置，且必须按身份和对象隔离。用户连续性不应以混用身份或重放写入为代价。

**三、C1/C2 已集成后的产品补充**

**11. C1 已有后台归档，但控制台附件体验仍需补齐。P1。**

当前 C1 已实现下载、重试、不可用处理、保留期清理和活动运行引用保护，不能再把这些列为待开发。

但当前 `localFilePath`是服务端路径，文档明确没有浏览器文件服务；时间线仍只展示文本。附件字段为空也不能向用户区分处理中、失败或已过保留期。[媒体当前能力](/Users/zcm/Desktop/kapibala/docs/c1-media-files.md:7)、[时间线展示](/Users/zcm/Desktop/kapibala/apps/web/src/components/Timeline.tsx:218)。

按“体验完整”的目标，建议至少补齐：

- 纯媒体消息可辨认，不成为没有说明的空白记录。
- 展示可证明的处理中、可用、不可用或已过保留期状态。
- 若产品允许操作者取回附件，提供受现有读取权限约束的有效下载入口。
- 不把服务器路径当作用户本机可打开的文件。
- 文件失效后保留消息事实，不展示假可用链接。
- 重试或重新获取仅适用于允许的情况，不能承诺过期来源必然恢复。

图片、音频、视频、文档的丰富内联预览，以及上传和外发媒体可以另列。后台归档不自动包含这些能力。

验收应覆盖纯媒体消息、下载失败、保留期结束和实际下载失败的兜底。

**12. C2 已有通用助手和审计策略，下一步应补业务结果验收。P1。**

新实现已经包含简短回复、不重复成功动作、不绕过审计、未知发送结果保持同一逻辑 key等策略；审计也已定义威胁、辱骂、诈骗、凭据泄露和绕权内容的拒绝规则。不能泛称“没有业务策略或审核规则”。[现有策略](/Users/zcm/Desktop/kapibala/apps/gemini-agent/src/app.ts:20)。

仍需补充的是面向目标业务场景的可接受结果：

- 什么时候回答、沉默或拒绝。
- 多条触发消息如何处理，是否允许合并回复。
- 缺少上下文、正文被截断、只有媒体没有可理解文字时如何结束。
- 正常结束但没有发送消息时，页面不能显示为已经回复。
- 运行摘要只作记录，不等同于群内回复或最终投递事实。

当前模型收到的是协议 JSON 文本，没有文件内容。因此，C1 归档不能被表述为 C2 已支持识图、音频转写或文档理解。[模型输入](/Users/zcm/Desktop/kapibala/apps/gemini-agent/src/provider.ts:54)。

验收应检查实际群消息、拒绝和运行结果，覆盖正常请求、多消息、缺上下文、纯媒体、诱导绕权及自动移除场景。合法 JSON和一条正常回复不足以证明完整业务体验。

群级个性化策略、多模态和更多工具不必一起增加。

**四、值得保留的中低优先事项**

| 建议 | 优先级与调整 |
|---|---|
| 序列未生效输入提示 | **P2**。模板占位符列表和空字符串说明已经存在；重点改为不存在步骤的 `stepVars`、未使用变量、切模板后的残留值提示 |
| 序列模板最小生命周期 | **P2，新补充**。同名模板应可辨认，支持复制后修改、归档不再用于新运行；既有运行不能跟随模板变化 |
| 审核拒绝原因 | **P2，新补充**。审计返回 reason，但当前主后端主要保留 verdict；若要解释拒绝，应保留可展示原因，历史没有记录时不编造 |
| 模型故障辅助说明 | **P2**。在保留原错误码和轨迹的基础上，区分可证明的内容拒绝、服务不可用等原因，避免全部被理解为用户输入格式错误 |
| 时间和消息定位 | **P2**。解释本地时区、排队时间与发送时间、迟到补投及已加载范围；核对结果所需的 ID 定位优先于全文搜索 |
| 无法操作时的下一步 | **P2**。说明缺少账号、角色不匹配、群已退出或不可写等实际原因；不必增加完整引导向导 |
| 消息、附件和诊断读取范围 | **P2**。明确 viewer 可查看、复制或导出的内容；不据此推断已经泄露，也不扩成租户或复杂权限平台 |
| 首次发送账号是否必须显式选择 | **P2/P3**。可以保留默认策略；重点是身份持续可见、已选身份失效后不静默换人 |
| 完整历史检索、统计、全局异常中心、跨设备草稿 | **P3**。待实际使用证明需要后再做 |

序列输入方面还有一个具体边界：目前 `stepVars`只校验步骤键格式，解析时只读取实际存在的步骤。因此，两步模板传入第三步覆盖值可能被忽略。[变量契约](/Users/zcm/Desktop/kapibala/packages/contracts/src/sequence-requests.ts:30)。预检应提示该输入未生效，并明确哪些情况阻止启动、哪些只提示，避免“全部通过”被理解为所有配置都参与了发送。

模板生命周期也是现有提案之外较有价值的补充，但首版无需完整版本管理或发布审批系统。

**五、建议的实施排序与提案收敛方式**

建议按以下顺序安排后续产品补全：

1. **提交正确**：输入保护、操作目标一致、预检摘要、结果未知核对。
2. **效果可解释**：部分失败仍处理中、运行结束与投递结果分离、审计阻塞和取消说明。
3. **业务可止损**：序列停止后续发送、退群期间动作边界、Agent 关开规则和自动移除政策。
4. **流程可找回**：导航返回、原任务定位、消息与运行关联、陈旧数据及身份变化兜底。
5. **C1/C2 可验收**：附件入口与不可用状态、真实助手的代表性业务场景。
6. 再补模板管理、输入便利、时间说明和高级检索。

提案中最需要先形成明确规则的，是**退群期间是否接受新操作、序列停止覆盖哪些消息、Agent 重开处理哪些旧消息、自动移除保护哪些对象，以及附件是否允许控制台取回**。这些会影响实际业务行为，不能只按“补几句文案”的成本估算。

本报告仅提出独立评估和范围建议，不改变既有实施决定。**报告未保存到项目中，未作任何修改。**
