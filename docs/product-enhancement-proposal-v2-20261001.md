## 产品逐项建议

<a id="input-protection"></a>
### 1. 提交与输入保护 · PI-03-b、PI-08

**现状与判断：** [Timeline.send](../apps/web/src/components/Timeline.tsx) 成功后无条件清空 text，提交期间 textarea 仍可编辑，存在旧回执清掉下一条草稿的源码路径；本轮未做浏览器慢回包复现。新建序列弹窗的 ×/Escape 可直接关闭；预检确认窗已有 busy 关闭保护，不能一并报告缺失。

**推荐最小范围：** 用提交快照/草稿修订标识判断只清本次输入；明确失败保留。新建序列窗统一提交中与未保存的关闭策略。允许用户继续输入是推荐方案；锁定输入也可作为更小实现，但需明确体验取舍。离页不代表后台请求已取消。不增加跨登录或跨设备草稿。

**验收：** A 提交慢成功时输入 B，B 保留；失败后可编辑；×/Escape/实际支持的其他关闭入口一致；预检或提交中离页不会错误说明已撤销。来源：IR-02/1、IR-01/R12。

<a id="target-preview"></a>
### 2. 目标、模板与预检上下文 · PI-14-b

**现状与判断：** [Sequences](../apps/web/src/pages/Sequences.tsx) 的预检保存 groupId/payload，启动使用同一快照；不是已证实“确认后换成新群发送”。风险是预检期间页面选择仍可变化，而确认内容缺少冻结群/模板摘要；选择 ID 不在返回列表时回退首项。这不等同群变不可写就必然自动换群。

**推荐最小范围：** 确认页展示目标名称/稳定 ID、模板、最终文本、角色、相对等待规则。选择变化使旧预检失效；已选实体失效后停止确认并要求重新选，不悄悄换成首项。切群/模板后的变量草稿推荐显式提示保留或清空，不跨目标静默提交。

**边界及验收：** 角色可用性仅是过期快照，运行时复检保留，不能因暂无角色取消原有 skipped 规则。测 A→B、预检未返回时切换、失效深链、模板改变和启动前账号状态变化。目标摘要不替代原变量预检证据。来源：IR-02/2。

<a id="unknown-request"></a>
### 3. 写入结果未知时核对原操作 · PI-09-c、PI-09-b 的最小部分

**现状与判断：** 浏览器未拿到响应不能证明服务器未受理。人工发送每次生成新 clientMsgId；当前同 ID 返回冲突，不是“重复请求复用原结果”的通用幂等接口。退群受理已复用同群仍在 running 的原 jobId，不能说所有重复提交都会新建任务。对应源码见 [Timeline](../apps/web/src/components/Timeline.tsx)、[messages](../apps/server/src/modules/gateway/messages.ts)、[jobs](../apps/server/src/modules/gateway/jobs.ts)。

**推荐最小范围：** 区分明确拒绝与受理未知；保留身份、目标、输入及可用关联 ID。优先 GET 原消息/任务/run，并展示查询范围和未确认事实；已有接口无法按可靠关联查找时，需要补本地持久关联或受权查询，不能仅估作改文案。无可靠原操作 ID 时不靠正文、时间近似自动认领。

**待选择的扩展：** 全平台 request key、payload 绑定、并发与保留期是 PI-09-b 的较大独立部分，P3 后置。只做核对不承诺安全重提所有未知操作；普通 404、消息 unknown 不证明未执行。任何网关去重或新增外部判据仍遵守 D039 排除。

**验收：** 服务端已受理、浏览器响应丢失时可以定位或如实标明不能定位，不自动 POST；同一意图和真正新操作分开，不误阻止合法同文发送。来源：IR-02/3、IR-01/R07。

<a id="effect-status"></a>
### 4. 流程状态、实际效果与下一步分开呈现 · PI-04-b、PI-10-b、PI-12-b、PI-16-b

**现状与判断：** [jobs](../apps/server/src/modules/gateway/jobs.ts) 的 errors 非空可对外报 failed，同时 processing=true；后者只表示内部尚为 running，可能正等待 nextAt 或 recoveryNote 核验，不等于正在执行或一定自动继续。[jobSchema](../apps/web/src/api/schemas.ts)未保留 processing，[JobProgress](../apps/web/src/components/JobProgress.tsx)按非 running 调完成回调。recoveryNote 已展示，应补状态组合而非重建已有暂停提示。页面误导场景待实测；不能据此判后台违反原 errors→failed 规则。

**推荐最小范围：**

- 消息受理与最终 sent/failed/unknown 分开；原工具 accepted 历史和当前投递结果并列。
- Agent 正常结束、仅记录摘要、已发送消息是不同事实；取消不撤回既有外部效果。
- “副作用未执行”限定为当前审计受阻调用，此前步骤可能已生效；终态 blocked 不提示审计恢复后自动续跑。
- 任务未终态、等待重试、暂停核验、已结束分别解释；序列处理计数不冒充发送成功率。
- 下一步只链接真实可用的读取、等待核查或停止入口，不生成“一键恢复”承诺。

**验收：** 前步已发后步受阻；run 结束后投递失败；只有结束摘要；退群 errors 非空而其他步骤继续；recoveryNote 暂停时不显示正在持续处理。核心审计/恢复机制的既有结论保持。来源：IR-02/4。

<a id="sequence-stop"></a>
### 5. 停止指定序列尚未完成的后续动作 · 新增 PI-24

**现状与判断：** [序列服务](../apps/server/src/modules/automation/sequences.ts)有定义、预检、启动及查询，未提供操作者停止指定 run 的入口。它是新增止损规则，不是原 B1 已要求的停止接口漏做；原 stopped 只定义为群不可写，不能未经兼容设计直接复用为人工停止。关闭 Agent 或断开账号也不能替代。

**推荐方案：** 管理员按 runId 请求停止；未开始步骤停止继续创建发送，已排队但未派发的消息在真实派发竞争下原子取消。已发送保留事实，在途/未知继续核对，不写成已撤回或确定未发送。保留“人工停止”和“群不可写”的不同原因，不影响其他群。是否新增状态、API 与持久停止标识须在实施方案中说明兼容性。

**验收：** 第一步已发、第二步限流排队、第三步未开始时停止；同时派发、重复停止及重启后结果一致。原始已产生效果不得重复执行。暂停后编辑/继续、重排期后置。需要选择完整最小规则后实施，不能只做按钮。来源：IR-02/5。

<a id="leave-in-progress"></a>
### 6. 退出处理期间的业务边界 · 新增 PI-25，关联 PI-06-b、PI-01-c

**现状与判断：** [leave-all](../apps/server/src/modules/gateway/jobs.ts)受理为任务，群可在完成前保持 active；现有“全部服务账号退群”确认已存在。原文规定退群顺序与失败后果，但未完整定义处理中与新发送/序列的关系，因此这是新增规则。

**推荐方案：** 在退群受理与业务保护建立的同一事务边界阻止新发送、新序列及新 Agent 运行；当前自动化停止后续编排，Agent 仍保留原 A5.10“当前步结束后取消”的语义，未派发队列的处置与 PI-24 统一。在途请求和已知/未知外部效果分别核对，不承诺即时撤回。公开 active/left 原契约是否需扩展应单独说明，优先用处理标志和任务关联，不机械新增枚举。

**必须先定的细节：** 建议部分失败后保留退出处理中限制，由操作者确认剩余范围再重试或明确解除；解除不自动恢复旧自动化。最终选择需与群主最后、失败账号保留、left 不可写及 D042 外部成员保留一致，不重新提问已确认的 members 语义。

**验收：** 活跃 Agent/序列/队列并存时开始退群；重复点击找回原任务；部分失败仍可看剩余服务账号/群主和下一步。确认文案说明不等于解散远端群。账号操作的影响摘要沿用 PI-01-c。来源：IR-02/6。

<a id="agent-policy"></a>
### 7. Agent 开关、重开与自动移除政策 · 新增 PI-26

**现状与判断：** 原 A5.10 明确关闭后在当前步结束时取消；当前实现先处理已准备步骤，不能把它改报为应立即打断的缺陷。事件资格与 tick 清理分散，快速关开对尚未绑定 run 的消息有时序风险，尚未运行复现。[Agent](../apps/server/src/modules/automation/agent.ts)、[事件入库](../apps/server/src/modules/gateway/events.ts)、[当前模型政策](../apps/gemini-agent/src/app.ts)。

**建议分开选择三条：**

1. **关闭与人工操作说明：** 请求停止、当前步结束、run 终态分开；Agent 与序列独立。人工回复不自动视作接管，先显示相关运行并链接。
2. **重开旧消息规则：** 推荐只处理重新开启后新接收且符合原资格的消息，关闭期间与关闭前尚未分配的积压不自动补做；已属取消/阻塞 run 的触发消息不隐式新建替代 run。此方案会改变触发资格和时序，需先对照 A5 及迟到补投规则说明差异；仅展示开关状态不能视为已实施。
3. **移除对象与依据：** C2 提示已要求具体管理理由、禁止提议移除 ownPlatformUserIds；建议把平台托管账号保护落实到主后端不可绕过的校验，并明确其他保护对象及业务理由。原 A5 只规定 autoKickEnabled、执行账号角色及审计，新增目标禁令属于业务政策，不能宣称已授权或现有后端越权。审计通过不证明目标事实上应该被移除。

**验收：** 慢步骤关闭、快速关开、关闭期间入站、迟到旧消息、人工/自动并行、受控模型请求移除受保护账号。先用可控协议桩验证机制，真实模型场景另按调用范围执行。来源：IR-02/7。

## 活动时间计量：已知风险与后续优化建议

2026-10-01，关联CG-08、A5.2、D040。负责人最初选择保留现状，重新评审后改为加强既有记账、不预扣预算；此前“只记录、不改代码”结论已被替代。[计量加固](core-activity-accounting-hardening.md)已完成80项定向及关联自测，整合交付见本轮收口。此项是内部计量边界，与上一节外部能力缺失分开；原始核心记录仍保留，不改称已严格满足。

| 类别 | 正式记录 |
|---|---|
| 实际机制 | ActivityClock每500ms尝试对可运行的run采样，数据库锁所有者负责持久计费；正常关闭尝试补记，硬终止不能保证执行清理 |
| 风险 | 最后一次成功保存到硬终止之间的在线时间可能漏计；数据库等待、事件循环阻塞可扩大间隔，多次硬终止可能累计少计，使实际在线运行时长超过名义预算 |

| 后续建议 | 先明确计量精度目标与故障范围，再评估关键边界持久化、采样滞后观测、故障接管和可验证的保守预算策略；每项须检查停机误计、重复计费、锁竞争与资源成本，不能只提高采样频率就声称严格保证 |
