# 全新隔离启动与清理验证

## 目的与范围

本入口让接收工程的人从任意克隆目录复现当前平台，不依赖开发者绝对路径、固定端口、已有数据库或模拟器状态。入口为 `npm run dev:isolated`，完整使用步骤见仓库 [README](../README.md#全新隔离启动)。它复用现有产品与模拟器工厂，不新增外部业务协议，也不启用 QA 控制接口。

本次是研发侧交付环境验证。页面入口、身份、代理、资源归属与清理通过，不能代替完整业务验收或独立 QA 结论。Agent 状态文件验证直接调用临时 Agent 模拟器已有的审计接口，仅证明该模拟器使用本次独立状态路径。

## 实际机制

| 环节 | 实际行为与保护 |
| --- | --- |
| 依赖 | 使用 `.nvmrc`、`package.json` 和唯一 lock 文件；从仓库根目录执行 `npm ci`。启动前检查 Node 版本与 Docker 可用性。 |
| 数据库 | 每次生成 UUID、随机数据库名和密码，创建有独占标签的 PostgreSQL 17 容器及命名卷；仅绑定 `127.0.0.1` 随机端口。先检查容器内 TCP ready，再通过真实宿主连接查询并迁移新库。 |
| 服务与页面 | 网关、Agent、API、Web 均使用 loopback 随机端口；Vite 以中间件方式接入自有 HTTP 服务，API/WS 代理指向实际 API 地址。它们由单个前台进程管理。 |
| 模拟状态 | 新建权限 0700 的 UUID 临时目录；网关、Agent 状态文件位于其中，不复用演示状态。 |
| 资源归属 | 私有 manifest 记录 PID、`ps lstart` 启动身份、Docker daemon ID、容器 ID、随机标签、卷和状态路径。manifest 含临时凭据，权限 0600；写同目录临时文件完成后原子 rename，避免进程中断截断原文件。 |
| 正常与失败清理 | 服务按逆序关闭；单项关闭超时记为失败，仍尝试核对归属后清理本次容器、卷与目录。信号处理器保留至异步清理完成。无 `pkill`、`killall` 或 prune。 |
| SIGKILL 后清理 | 用户明确传入启动日志里的 manifest。校验用户、权限、规范路径、UUID、真实进程身份、daemon 和资源标签。原 owner 仍存活时拒绝；PID 被其他进程复用时也不向它发信号，只清理匹配标签的旧资源。 |

## 边界与失败处理

1. 该环境一次性使用，正常退出即删除本次数据。正式演示数据及历史备份不适用此入口。
2. 本次实际验证在 macOS 完成；实现使用 macOS/Linux 的 `ps`，尚未将 Linux 实机结果写为已验证，也不声明支持 Windows 或远程 Docker daemon。
3. SIGKILL 无法运行退出处理，需要用保留下来的 manifest 执行显式清理。原子 rename 防止已存在 manifest 被半写覆盖，不等于对断电持久性、磁盘损坏或所有 Docker 创建竞态作保证。
4. Docker daemon 不可达、归属不明或卷仍被占用时，清理失败并保留可用的 manifest。不要手工删除未知资源；恢复相同 daemon 后按归属信息重试。
5. 服务关闭超过 5 秒会记录失败；最后的进程退出能关闭本进程句柄，但不将超时宣称为优雅完成。若资源已删而局部关闭报错，应以日志中各项结果区分。
6. README 的启动步骤及 `--smoke` 可重复执行。故障演练只作用于本次独占实例，不通过已有演示环境、独立 QA 资源或默认测试库获取证据。
