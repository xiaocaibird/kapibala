## 已确认行为

序列某一步出现**不属于原有跳过规则的普通发送失败**时，该步骤应真实记录失败，整条运行进入 `failed`，后续步骤不再发出消息。此前已经成功发出的消息不撤回、不改记失败；原失败信息保留，不能把失败步骤伪装成 `skipped` 或把整条运行记成成功完成。

适用示例包括已选定发送账号后的 `ACCOUNT_OFFLINE`、`SENDER_NOT_IN_GROUP`，以及发送结果曾不可确认、随后已按照原 A2 规则明确收敛为 `failed` 的消息。原消息的结果确认规则不因本裁定而变化：by-client-id 查询不可用期间保持 `unknown`，序列不得因暂时查不到结果就结束或继续后续步骤；恢复查询、确认失败后才按本裁定结束运行。

原 A2 允许在确认未发出后使用同一个 `clientMsgId` 重发一次，并非必须重发。测试同时接受不重发而确认失败，或最多重发一次且仍未发出后确认失败；不能强迫产品执行可选重发，也不能在结果未确认时重发。A2 的原有确认时限仍有效，不由本裁定新增或放宽。

终止后应遵守原运行终态及活动引用约束；读取、等待或应用重启不能使本次运行自动恢复后续发送。需要再次执行时，用户应按正常入口新建运行，不把原运行中的后续步骤当作隐式续跑。

## 与原有分支的边界

| 情况                                   | 验收行为及依据                                                                                 |
| -------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 角色选择阶段没有匹配账号               | 按 B1 保留 `skipped`，有时间戳，进度继续；不是本条普通发送失败。                               |
| 账号 `rate_limited` 或发送收到 429     | 按 B1/A2 顺延、同账号队列等待；不能为尽早结束而改判普通失败。                                  |
| 消息仍为 `unknown` 或尚在确认中        | 不得仅因观察超时、查询暂时失败或没有后续事件就套用本条；先按 A2 完成确认，未确认即保留原语义。 |
| 已按 A2 规则明确成为 `failed`          | 适用本条：步骤和运行失败，后续不发送。                                                         |
| 群已不可写，按原群生命周期规则停止运行 | 保留原 `stopped` 及群状态联动，不改成此处的普通 `failed`。                                     |
| 上一步 `sent` 或 `skipped`             | 仍分别按收到 `message_sent` 或跳过时刻计算后一步排期，`R-B1-07/08` 的原断言保持有效。          |

本裁定不新增任意毫秒级终止 SLA、不定义原规范未规定的内部处理优先级，也不授权放宽重启后不重复副作用等强要求。有限测试采样不能证明任何未来时刻都不会发送，报告应保存实际观察窗口、请求和外部消息账本。

## 自动化组合与证据

`BLK-SPEC-002` 的同一正式入口包含两类组合，不能只以同步错误覆盖代表全部普通失败策略：

- `ACCOUNT_OFFLINE`、`SENDER_NOT_IN_GROUP` 分别发生在首、中、末步骤，共六种同步失败组合；中间步骤失败另检查外部故障解除及应用重启后不复活后续发送。
- `NETWORK_TIMEOUT` 后暂时关闭 by-client-id 查询，验证 `unknown` 期间不结束运行、不发送后续步骤；随后恢复查询并确认没有发出，若产品选择重发则使唯一允许的重发也未发出，验证消息最终 `failed` 后运行 `failed`、后续不发送。

每类组合都核对独立请求/实际消息账本和公开运行状态；异步组合分别保存查询故障窗口、恢复时点及确认结果。`unknown` 期间未发送后续与确认失败后停止后续是两个不同断言，不能用一次最终状态检查替代。上述内容描述自动化设计，尚无产品执行证据。
