## 为什么需要调整

ARC-UI-015 原先检查耗尽后的请求数及序列选中值，但未排除点击刷新时重新加载整个 document 或重建公开 scope；也没有把恢复结果绑定到真实成功响应。UI-032 已证明两页数据与真实 cursor，但确认时可能由整体刷新/范围重建清掉提醒，从而无法说明旧多页的过期状态与提醒相互独立。

依据仍是 [ARC-UI-015](../../cases/architecture-ui.json) 的 ENG-READ-01 与 [UI-032](../../cases/ui-extra.json) 的 ADD-ATT-05/ADD-DIR-08，不新增页面、流程或时限。

## 新增的证据约束

- 在登录前建立被动监听，记录主 frame 导航、真实 WS 建立/关闭及公开 `scope_ready`；动作基线保留 document 句柄和 URL。比较后记录 sameDocument 及前后计数。没有公开 scope 起点或窗口被替换时不得冒称原页面恢复/确认。
- ARC-UI-015 保留原四次失败耗尽与后续一次成功的版本参数及观察窗；新读取必须返回真实 200、含预先通过公开 API 创建的序列，并成功呈现其选择。请求次数、响应内容、连续性及无其他业务事件分别留证。
- UI-032 确认前后保留原 23 个有序群 ID、查询控件值、真实首页 cursor、第二页响应、过期提示与无后页请求事实。不读取产品内部 scope/cursor；允许不替换旧多页的合法首屏探测，不能仅因有 GET 就判整体刷新。公开旧 cursor 的禁止使用与当前已呈现身份是可验证边界。
- 不生成新的定位器，不调用业务内部 reload/确认函数，不通过整页 reload 或 DOM 赋值制造前提。研发仍需交付可公开验证的同页刷新入口，以及独立于整体刷新、能合法确认已呈现变化的入口。不存在或无法适配时继续 BLOCKED。

## FAIL 与 BLOCKED 的先后关系

业务断言前后都检查同一公开连续性边界。若断言在该有效窗口内已明确失败，记 `confirmed-business-failure`；稍后的最终检查再发现导航/新 scope 时，保留原 FAIL，并同时保存后来的连续性错误。

标题或 locator 等待若跨越了 document/scope 更换，就没有充分证据认定是原页面业务违约。其原始错误仍保留在 assertions 中，但结果为 `blocked-continuity`。连续性有效时同一断言真实失败仍为 FAIL；正常断言全部结束后才出现范围污染，也不能以先前成功提前通过。

这个规则不是“所有首次异常都优先”，而是“已确认的业务违约优先于后来的前提污染”。断言依赖的前提已经破坏时，不把等待超时硬升级为产品 FAIL。作用域内部是否更换不可由黑盒完全证明，报告只声明实际 document、URL、导航、连接、公开 marker 与可见条件的有限观察。

证据对象同时保存 primary、confirmedBusinessFailure、boundaryErrors、逐组断言及连续性检查。窗口关闭/取证的二次错误保留并输出；不得覆盖已确认的主错误。历史首次 FAIL/BLOCKED 记录不重写，新执行结果须另行固定版本与证据。
