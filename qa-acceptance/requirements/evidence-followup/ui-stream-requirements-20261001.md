## ARC-UI-015：耗尽后显式同页刷新

### 依据与旧事实

- [用例](../../cases/generated/architecture-ui.md#ARC-UI-015)、[现有自动化](../../tests/ui/architecture.spec.ts)：对应 `ENG-READ-01`，持续 503 耗尽后恢复服务，通过真实同页操作启动新一轮读取。
- [公开读取恢复约定](../../../docs/architecture-quality-closeout.md)说明最多追加三次读取、250/500/1000ms 退避，以及耗尽后可由新的显式刷新、事件或轮询触发新一轮。具体参数属于版本策略；原要求不因此变成必须精确命中某个调度毫秒。
- 旧正式运行 `2026-10-01T06-54-18.519Z-a1e23916` 的 [请求记录](../../reports/runs/2026-10-01T06-54-18.519Z-a1e23916/artifacts/ui-architecture--ARC-UI-015-耗尽后显式同页刷新可开始新一轮-chromium/evidence/architecture-browser.json)有四次 `/api/sequences` GET/503；之后无新业务事件。其 [页面记录](../../reports/runs/2026-10-01T06-54-18.519Z-a1e23916/artifacts/ui-architecture--ARC-UI-015-耗尽后显式同页刷新可开始新一轮-chromium/evidence/architecture-final.json)显示序列页及错误文案，没有展示重试操作，原结果为 BLOCKED。这里依据实际 503 耗尽记录，不拿更早的 403 页面观察代替本场景。

### 最小公开接入

研发交付准确的候选 SHA、角色、路由、达到持续 503 耗尽状态的方法，以及在该状态实际可见的操作名称、区域和可访问角色。可以是既有操作，不要求新增名为“重试”的按钮；但必须真正作用于当前序列资源，并保留当前页面生命周期。若该页没有这种操作，明确说明，先判断是文档契约未覆盖该页、测试路径需调整，还是应补的产品能力。仅凭现有选择器未命中不能判产品 FAIL；也不能据此宣布已恢复。

QA 适配 `sequenceResourceRefresh` 的真实定位/操作，补充以下外部证据：

1. 登录后的真实 WS 回放已稳定；从可见导航进入序列页且 document 不变。每次 GET 的开始、结束和受控 503 完整记录；按该候选已确认策略达到耗尽，再保持原 3000ms 负向观察窗。
2. 保持同一 document、路由、用户会话及 WS 连接；先恢复该 GET 的真实网络响应，再操作。不得借新事件、轮询、重新认证或页面重建让恢复自动发生。观察窗混入这些独立触发时，记录并 BLOCKED，不把它们归功于点击。
3. 在操作前后保留 document 身份比较、导航事件和请求时间线；仅“URL 一样”不足以证明未整页重载。只读取 document 身份用于观察，不调用业务控制器或修改页面状态。
4. 真实成功响应及预置序列可见；新一轮成功读取后请求数稳定，页面保留当前上下文。沿用现有版本 profile 的一次成功读取及无额外请求断言，候选若明确调整重试策略需先版本化记录，不能照实测数量倒改预期。

**不可接受的替代**：`page.reload()`、`goto` 同一 URL、离页再返回、注销重登、手工发送 WS 事件、在页面执行 `reload()`/hook、只用 GET 200 或错误消失代替资源实际呈现。

**结论**：前提和真实入口已确认后，恢复成功且保持无额外触发/稳定读取才 PASS；操作无效、恢复错误或已确认的重试策略被违反为 FAIL。没有可达公开入口、未建立耗尽或独立触发污染仍 BLOCKED，具体写明接入缺口；不把 8 秒 QA 等待预算泛化为新的业务 SLA。

## UI-032：确认提醒不得恢复过期 cursor

**2026-10-01 后续判据更正：** 下方保存原补证阶段的来源与设计。原23条数据虽形成两页，但第二页没有剩余cursor；要求只显示旧内容且仍stale时独立确认也不是批准规则保证的前提。本轮后续自动化改为至少`2P+1`条、两整页及非空剩余cursor，先验证失效/503失败刷新保护，再以真实成功整体刷新和新结果/范围摘要建立合法确认资格；确认本身不得改变新分页资格或恢复旧链，随后真实续页来源必须是新响应。当前步骤与阶段边界以[收尾契约U1–U6](static-closeout-contract-20261001.md#下一候选公开流程)为准；原stale且新目标已呈现的联合构造仅作可选增强，不能再作为本项必需前提。旧结果与原始证据不改，修订未运行产品。

### 先确认场景可达，不能要求无条件清提示

公开规则区分“具体目标的新版本已成功呈现”和“当前查询可能变化、尚需刷新核对”。范围候选、未知目标、未呈现内容不能仅点通用提示就确认。现有多页元数据变化场景并没有证明修改后的内容已成功呈现，因此不能把缺少 `attentionConfirm` 按钮直接定为产品缺陷，更不能把“刷新并查看更新”改名当独立确认。

研发最小交付是一个符合既有规则的可复现路径：在**同一查询、同一页面生命周期且目录仍 stale**时，某个待确认目标的新版本已通过公开路径成功呈现；用户能对该目标真实点击/键盘操作或使用明确确认操作，确认不会整体刷新目录、切换查询、导航离页或重建 scope。说明目标身份、变更字段、成功响应/可见文本证据、操作区域、确认范围与其他未确认候选的处理。优先解释已有路径，不要求固定控件名称或新增确认能力。

如果所有可达路径都必须先整体刷新，而成功刷新依法解除 stale，那么该路径不能证明本用例的独立性。研发如实说明即可；QA 保留 BLOCKED 并记录“现有公开交互未建立该组合前提”。是否需要补能力或调整测试构造必须有原需求/公开契约依据，不因此扩大为待负责人重新设计整个提醒功能，也不静默删例或计 PASS。

### QA 可直接补的窗口与取证

1. 复用 `DirectoryLedger`，登录前开始被动记录实际 `scope_ready` 与事件水位；保留原五秒稳定窗口。首屏、确切 cursor 的第二页、完整 23 个身份与 DOM 顺序相符后才进入故障窗口，不靠随机 sleep 或额外 `goto`。
2. 使用真实标签失焦并核对 `hasFocus`/visibility；在当前查询内制造相关变化，确认 stale、提醒标题及旧列表保留。不得覆写焦点 API，也不将仅 `bringToFront()` 当确认。
3. 按交付路径建立确切目标的成功呈现证据，再执行真实相关操作。若该构造引入额外范围候选，逐一记录，不能在仍有合法未确认项时强断言全局标题清空；如需更换构造，保留“对应提醒确认不改变 stale/旧 cursor”的原断言，先记录变更依据。
4. 保存确认前后的查询身份、document/scope 水位、旧 cursor、已加载身份/顺序、stale 提示和所有目录请求。提醒确已确认后，旧 cursor 仍不可用，加载更多不存在或禁用，原负向观察窗内无续页请求。候选允许的五秒首屏探测可以发生，须单列，不得把合法探测误判为用户整体刷新或后页请求。
5. 当前脚本已观察续页请求；需要补全“本次确认没有触发整体替换/切 scope”的证据，避免仅因为列表变成新第一页而看不到加载更多就判 PASS。后续手动整体刷新属于另一动作，只有它成功后才能依据新第一页和新 cursor 继续读取，不与确认动作合并取证。

**不可接受的替代**：清 title/favicon、修改 store/内部已读状态、调用 attention 方法、无关点击、仅聚焦、换筛选/离页导致 scope 销毁、整页刷新，以及把刷新成功后旧 cursor 自然废弃当成确认与 stale 独立的证明。

**结论**：合法前提建立后，相关候选按规定确认且 stale/旧 cursor 禁用保持才 PASS；未呈现即确认、确认恢复旧 cursor/消除 stale/改缓存，或真实续页使用旧 cursor 为 FAIL；公开操作或成功呈现前提仍缺失则 BLOCKED。旧 23/20 FAIL 和后续 BLOCKED 都原样保留，不回填。

## INT-STREAM-001：真实慢读、健康对照与接收游标回放

### 依据与旧事实

- [用例](../../cases/generated/integration-streams.md#INT-STREAM-001)、[现有自动化](../../tests/system/integration-streams.spec.ts)、[真实接收器](../../harness/receipt-socket.ts)对应 `ENG-STREAM-01`、`R-A4-03/04`；[公开资源边界](../../../docs/core-resource-observability.md)及 D044 允许关闭真实慢连接、保存持久事件并按客户端实际已收 seq 重放，同时保持健康消费者工作。
- 旧 [原始接收账本](../../reports/runs/2026-10-01T06-54-18.519Z-a1e23916/artifacts/system-integration-streams-344ee-ived-cursor-replay-complete-system/evidence/real-reader-receipts.json)的暂停 checkpoint 为 13，慢端只有 auth 和 checkpoint 两帧；已注入 960 条目标消息，健康端实际收到 928 条目标消息（共 930 帧），无记录错误、未创建 replay 连接。[原归因](../../reports/acceptance/20261001-business/triage-final-stream.json)因此维持 BLOCKED：45 秒有限注入阶段未得到完整健康集合，没有证明关闭、缺口或恢复。
- 2048 条、每条 8192 字节文本是旧 QA 负载上限，不是已注满的事实。WS 最小 message 协议不要求携带完整 text；原接收投影没有 text 哈希，不能把正文大小乘消息数当成真实 WS 传输字节。先测实际帧字节，再决定合法负载，不为了顶水位向产品帧添加非协议字段。

### 最小环境、控制与独立观测

正常公开启动、真实专属 PostgreSQL、QA 网关注入、两个独立认证 WS 已足以作为起点，不先要求研发新增业务 API。控制对象只限 QA 自有读端或其真实传输路径：

- 在两个连接实际收到 checkpoint 后，调用真实 `ws.pause()`/底层读端暂停，记录暂停成功、单调时钟、实际已收 seq 和帧数。暂停期间不能消费后丢弃消息来伪造未读；恢复读取前保存证据。
- 健康端始终正常读取，逐帧记录实际接收时间、字节数、seq、身份及公开必要字段。注入的稳定身份和内容哈希来自独立网关台账，公开历史按该集合核对内容；全局 seq 可有其他事件形成的间隙，不能臆造连续整数要求。
- 记录关闭发起方证据及时间：慢端真实收到对端关闭/断流、关闭码/原因（若有）、QA 尚未主动 cleanup 的事实。1006 或单独 socket error 不足以证明慢消费者策略命中，需排除 QA 限额、自行 terminate、代理错误、进程退出或普通网络故障；健康连接和 SUT 同期状态作为对照。必要时使用与连接 ID 可对应的只读传输诊断，而不是由控制器直接宣告“通过”。
- 恢复读端并排空已在途缓冲后，以慢端**最后完整实际收到**的 seq 重连；保留旧连接前缀、缺失集合、重连 auth 的 sinceSeq 和新连接尾部。必须有非空真实缺口，旧前缀与 replay 合并后恰好覆盖全部目标身份、无重复且有序；继续原 1000ms 观察迟到重复。
- 健康端必须最终覆盖全部独立已注入集合，不把“仍有几条消息到达”当完整对照；公开历史也须完整且内容一致。认证控制帧不推进持久事件游标，不能拿健康端或服务端 attempted-send 游标替代慢端游标。

### QA 可直接修的负载与预算

先把负载、注入、健康端排空、关闭观察和 replay 分成有证据边界的阶段。旧脚本在每批 32 条后等健康集合，45 秒到期就退出；新 profile 可在明确的总资源上限内增加观察预算、调整批次/速率，并在停止注入后单独给健康端完成窗口，保留所有首次尝试记录。延长等待只帮助建立前提，不将旧 BLOCKED 改为消息丢失，也不令任何已观察协议错误消失。

配置应列出最大消息数、实际帧/总字节观测、速率、各阶段时间、接收账本/内存上限、历史遍历页数和总时限；同时调整目前 8192 帧 QA 账本及页面上限之间的一致性。只允许有限、可清理的隔离实验，不能为命中关闭无限加压。到达 QA 上限而无违约证据时 BLOCKED。

可选择经审阅的 QA 自有传输控制，使一个真实连接更早承受背压；若使用透明 TCP 中继，必须有有限缓冲和真实暂停上游读取，不伪造/丢弃/改写应用帧，不由中继主动关闭冒充服务器关闭，完整保留中继和两端的方向、时间与清理证据。对中继自身错误保持 BLOCKED，不能据其自报替代产品侧事实。能仅用直连真实暂停建立场景时优先直连。

### 研发最小交付

1. 固定候选、启动命令和正常公开 WS/鉴权/重连协议引用；说明该候选合法事件来源、公开载荷限制，以及能制造真实慢读的有限负载建议。建议必须通过公开行为生成事件，不直接写事件表或导入产品发送器。
2. 说明当前真实部署使用的版本参数和边界。现有公开文档的默认水位 1 MiB、发送回调等待 5 秒、关闭兜底 1 秒是实现参数，不能解释为全进程内存上限、生产吞吐/关闭 SLA。研发已有使用 1 秒/50ms 的内部专项记录只是开发机制证据，不代替独立 QA 默认配置验收。
3. 仅在外部观察不足时，交付最小只读传输诊断：实际连接关联 ID、队列/缓冲或发送等待的实际观测、真实关闭原因及时间、来源位置和是否默认启用。不得让 QA 通过注入发送成功/失败回调、直接关闭 SUT WS 或调低内部常量来判生产配置通过。若仅能提供特殊装配，单独绑定并标注机制验证范围，默认配置义务继续保留。
