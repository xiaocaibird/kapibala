# QA 信息交接与变更影响检查

QA 独立维护预期、用例与结论，同时主动获取需求、技术方案、假设、变更和已知风险。需求映射齐全只是结构检查，不能代替风险场景充分性评审。开发方的测试结果是线索和交接材料，不直接成为独立 QA 的 PASS。

## 固定交接节点

| 节点              | 技术侧提供                                          | QA 核对并回传                                              |
| ----------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| 需求冻结          | 已确认范围、公开契约、争议及暂缓项                  | 可测试性、判定依据、需求缺口、验收入口                     |
| 技术方案评审      | 状态/事务边界、外部副作用、恢复策略、容量与时序假设 | 通用故障和组合风险、可控故障点、可观察证据、需要的测试接口 |
| 关键方案/实现变更 | 精确版本差异、外部行为与兼容性、已知限制            | 原用例继续适用部分、补测范围、执行适配及判定依据           |
| 开发提测          | 固定候选、启动/迁移命令、配置、开发自测与未闭合问题 | 执行前检查、版本差异闸门、环境隔离、待授权范围             |
| 阶段性风险复核    | 新发现、失败反例、环境变化、修复版本                | 横向检查同类问题；维护缺陷、阻塞和复测关系                 |
| 执行与复测完成    | 修复说明与影响范围                                  | 独立证据、实际结论、剩余风险、需负责人裁定的偏离           |

阶段性同步随上述节点发生；较长阶段由主任务约定节奏。这里定义流程，不创建定时任务，也不自动向其他聊天或外部人员发送消息。信息可来自共享文档和已授权的任务交流。

## 交接最小内容

1. 比较起点与候选版本；改了什么、为什么改。
2. 需求与公开契约是否改变；任何新增条款的明确来源。
3. 影响的状态、资源、依赖、权限、计时、幂等、兼容和恢复边界。
4. 需要交叉检查的反例：依赖不可用、资源耗尽、没有后续触发、重复乱序、取消/预算/政策交错、重启及清理失败。
5. 用什么公开观察证明测试确实触发了目标条件；不能仅从“没有输出”推断某内部拒绝分支发生。
6. QA 结论：不影响／增加回归／修正适配／补齐用例／依赖待澄清；列具体用例与证据。

## 自动化与人工判断分工

`requirements/change-reviews.json` 记录已评估版本与评估材料。验收入口启动任何产品进程前，对候选与已评审版本做 Git 差异核对；产品代码、迁移、契约、启动配置及关键需求/架构文档发生变化时，先完成影响评估。QA 目录或与验收无关的证据归档改动不会被当成产品变更。

这个检查只能阻止未经评审的变化直接进入执行，不能自动证明评审充分。`risk-coverage-review.md` 必须诚实说明已有、部分覆盖和缺口；未知参数或缺少可控故障接口不能从当前实现倒推答案。补用例时保持原要求，对未裁定或不可观测的部分登记 BLOCKED；不要求技术侧只为了测试暴露私有状态或改写业务语义。

当前阶段只准备和校验 QA 资产。变更影响评审、QA 自检或开发方自测均不构成实际产品测试授权。
