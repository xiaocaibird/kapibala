# 容量准入专项的观察与故障控制契约（待提供）

本文件定义独立 QA 完成 AR-04 验收所缺的外部观察能力，不修改产品，也不把这些能力擅自增加为生产业务 API 要求。适配方式须先确认并随测试版本、目标版本冻结；实现方自测日志和历史通过结论不能替代本轮独立证据。

依据：`docs/decisions.md` D036、`docs/architecture-reviews/2026-10-01-baseline.md` AR-04，以及原始 A5 的审计、权限、活动预算、取消和恢复要求。`docs/architecture-quality-closeout.md` 描述的是待验行为，不是通过证据。

## 已能执行的公开边界回归

`CAP-REG-001..004` 仅操作 REST、Agent 协议与网关协议：跨群请求重叠；审计响应等待期间关闭踢人政策；执行账号离线；管理员成员移除与普通成员角色限制。每条记录 runId、toolUseId、审计原文、公开步骤与网关请求/真实副作用。

其中审计屏障意味着审计尚未回答，网关 request 屏障意味着远端已经收到请求。二者均不能证明本地容量拒绝。并发回归即使通过，也不能关闭 `CAP-001..010`。跨群采用同名外部目标来检查群隔离，但不同群的目标不构成同一实体锁竞争。未建立请求重叠时记录 BLOCKED，不能把串行执行当作并发通过。

## 容量分支的最低证据

后续确定性用例需要一个可从被测进程外使用、经过确认且仅绑定本轮隔离资源的控制/观察适配器，至少提供：

1. **可关联的准入结果**：实例身份、groupId、runId、toolUseId、单调事件序号、时刻/区间，以及 `capacity_unavailable`、`lock_busy`、`executed` 三类语义。名称可以不同，语义和关联不可丢失。不能只记录“繁忙”或只给全局计数。
2. **拒绝边界**：明确目标尝试在受保护操作回调与远端派发之前被拒绝；与同一时间线的独立网关请求账本交叉验证零请求、零实际效果。短时间没看到请求并不足以证明该边界。
3. **可释放的容量占用**：公开操作形成的持有者集合，或经批准的外部故障控制入口；返回可观察占用已建立的证据，能够保持、释放指定持有者，且不替应用额外补出幂等或收敛。配置值只用于试验布置，不作为生产容量指标。不能依赖固定槽数或睡眠时长碰运气。
4. **与实体冲突分开**：能保持同一业务实体被其他合法执行持有，同时证明尚有本地容量，再放行目标尝试。原公开“同群最多一条活跃 run”会阻止直接发起两条同群 Agent kick，因此不能假造未约定的手动 kick API 或写私有锁表。
5. **精确崩溃窗口**：为 `CAP-009` 提供“已经报告零远端的容量拒绝，但可恢复就绪状态尚未持久”的可停住/确认窗口。仅在审计响应、网关请求或响应处杀进程不命中这个窗口。不得为提高成功率而读取业务私表、导入内部 Database、改业务代码或重写状态。
6. **原预算测量**：记录 run 创建/活动开始及暂停恢复的权威时间或可包围它们的观察区间。拒绝等待消耗原 60 秒活动预算；不把每轮重试重新当起点。时间区间跨过边界时应 BLOCKED 复核，不能擅加容差。故障占用者本身失效、审计/turn 超时或进程重启的时间必须单列。

控制资源需绑定本次运行、明确所属实例和释放状态；中途取消、异常和清理均必须释放。单纯宣称“已饱和”的配置或人工复选框不构成证据。

## 判定与解除阻塞

`CAP-001..010` 在用例清单中为 blocked，报告初始仍为 NOT_RUN；未授权前不执行。取得上述能力后，应按各用例实际完成步骤、补充真实自动化入口并通过静态追踪检查，才可改成 automated。已有公开回归无需等待此适配器。

- 未触发或无法证明目标分支：BLOCKED，附缺少的关联/控制证据。
- 已确证容量拒绝后仍伪造 SEND_TIMEOUT/实体冲突、发出远端请求、重复审计或违反明确政策/预算：FAIL。
- 真正远端请求已发出、效果未知：沿用原协议确认与恢复要求，不能因容量不足把该步骤复位并重放。现有 `AGENT-029`、`REC-007` 与 `BLK-EXT-004` 保留各自强保证与阻塞，容量改动不放宽它们。
- 容量释放后正常完成，只有在同 runId、同 toolUseId、一次审计、一次实际 kick、终态及成员一致性均有证据时才算该有限场景 PASS；不是任意时刻恢复的全面证明。

目标成员在延期中退出/重入的具体工具返回语义尚无独立确认记录，`CAP-007` 同时保留该语义澄清。执行成员的在线、成员关系及管理员角色要求已有原文依据，不能因没有容量控制而混同为业务歧义。
