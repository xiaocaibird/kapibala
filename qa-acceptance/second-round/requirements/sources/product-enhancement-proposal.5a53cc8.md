## 20 小时安排与停止扩围条件

以下以本轮提出时剩余约 20 小时为总额，材料整理和确认耗时也要扣除，不能在选完后重新获得 20 小时。已运行的首轮 QA 收尾继续推进，其实际占用计入下表。前端实现为一条主线，后端质量/证据与接入准备为另一条；各自隔离资源，最终只有一个集成候选。

| 相对时段 | 工作与出口 |
|---|---|
| 0–1h | 核对当前基线、已有决定和 P0/P1 选择；整理首轮报告；确定 C1/C2 接入契约与明确入口 |
| 1–9h | 两条主线并行：前端完成 P0-03/04，后端完成 P0-05 及 C1/C2 接入准备；定向自测随改随做；只在不影响主线且有实测余量时排入已选 P1 |
| 9–10h | 集成、构建、原文校验和必要全套回归；修复明确冲突；冻结产品源、QA 源、配置及证据目录 |
| 10–15h | QA 独立做变更影响复测、C1/C2 已选范围验证和关键流程回归；已验证且未受影响的旧结果按版本引用，不冒充重跑 |

| 17–20h | 修复验收发现的问题、定向复测、最终报告及交付清单；保留完整 3h 返修和环境缓冲 |

- **第 7 小时检查一次余量**：P0 前端或质量工作预计无法在第 9 小时完成，立即取消未开始的 P1；已做 P1 若仍不稳定，隔离后退出候选。
- **第 9 小时停止加新功能**；第 10 小时后只处理交付阻断及当前候选的明确缺陷，不以扩大建议范围挤占验证时间。
- C1/C2 接入未具备、首轮出现新的实质缺陷，优先使用剩余工程时间；任何已选项取消或未完成都要进入报告，不能通过缩减断言制造按期完成。
- 没有要求改造全平台历史存储、队列、模型协议或认证体系。遇到这种依赖，停止该增强并记录替代范围；其他项继续。
- QA 至少预留 5h、人工体验 2h、返修 3h。执行中若这些时段已无法保障，应减少增强范围并明确交付风险，不压缩成仅构建通过。

<a id="input-protection"></a>
## P0-03：旧回执不能清掉新输入

[人工发送](../apps/web/src/components/Timeline.tsx)成功后目前无条件清空文本，等待期间输入框仍可编辑，存在 A 的迟到回执清掉 B 草稿的代码路径。新建序列窗的关闭回调未统一阻止保存中或脏表单关闭；预检确认窗已有 busy 保护，不能重复报为缺失。本轮方案整理仅核查源码，新的慢回包反例尚未执行。

**最小方案：** 提交快照绑定群、账号/会话、文本和草稿修订号。只有仍对应本次提交的草稿才清空，不能仅比较字符串；A→B→A 同样视为新编辑。失败保留输入。新建序列窗复用已有表单保护思路，所有实际关闭入口使用同一策略，保存中不让内容与提交快照分叉。

**交付断言：** A 慢成功时 B 保留；A→B→A 不被旧回执清掉；失败仍可编辑；切群/身份变化后旧响应不清新上下文；×、Escape、取消及实际支持的遮罩入口行为一致；已有建群/编辑群保护不回归。

不做跨设备/持久草稿，不承诺请求失联后安全重复发送。受理未知的原操作找回仍是独立建议，见下方保留表。

<a id="target-preview"></a>
## P0-04：确认的目标必须可见且仍然有效

[序列页面](../apps/web/src/pages/Sequences.tsx)已经以冻结 groupId/payload 启动，不能描述成后台把已确认请求发给新选择的群。当前缺口是晚预检响应仍可写回页面、确认窗缺少冻结目标摘要、显式选择失效可能回落到首项。

**最小方案：** 群、模板、变量等预检上下文携带修订号；任何相关修改都让旧预检失效，旧请求返回不得恢复可确认状态。确认窗展示冻结群名及稳定 ID、模板、最终文本、账号角色与相对等待规则。初次默认选择与已经选择后失效分开；后者要求重新选择，不静默跳到另一群。URL 已指定的群同样属于显式目标，失效深链不得按初次默认选择回落首项。

**交付断言：** A→B、A→B→A、预检未返回时改变量/模板、目标从列表消失、失效深链、确认前账号角色变化。原服务端预检、运行时校验、角色缺失时 skipped、限流顺延和排期语义保持不变；展示快照不构成未来账号可用的保证。

## P0-05：少量关键规则有明确入口，也能检出错误实现

已有真实数据库竞争、故障测试和修前失败记录，不再补一套镜像测试。新增范围限定为：

1. **两条固定检错实验：** 首选审计非 pass 不派发、同 key 复用原消息不重审不重发。在临时副本对指定守卫做最小错误改动，要求原实现通过、错误实现于对应业务断言失败，核对真实远端调用数和数据库结果。编译失败、数据库不可用、夹具错误或挂死都不计为检出。实验记录源提交、补丁、命令、原始结果及清理；不把错误补丁合入产品，不修改 QA 断言，不引入全量变异框架。CAS、失权旧执行者的现有用例继续回归；更多变异仅在同一预算有余量时追加。
2. **一个职责入口：** [automation/lifecycle](../apps/server/src/modules/automation/lifecycle.ts)已有 requestGroupAgentCancellation(tx, groupId)，但 [gateway 开关](../apps/server/src/modules/gateway/index.ts)仍重复更新 agent_runs。复用这个现有入口，保持调用方事务、CAS 成功后取消、锁及事件顺序。不能为了模块分离改成提交后的异步通知。
3. **有限机器检查：** 记录本次涉及的表/规则归属，检查已列出的跨模块写入入口；用一处受控违规样例证明检查会失败。规则要能区分允许的事务协作与重复直接写入。说明检测范围，不把文本扫描说成完整 SQL 所有权证明。

自测重点是关闭 Agent 的取消请求、当前步结束语义，以及失败时群修改和取消后果仍在同一事务中回滚。静态检查纳入已有开发验证命令；QA 独立维护它的业务验收。此项收口一个确定重复入口，不启动全模块重构。

<a id="database-measurement"></a>
## P1-01：一个真实数据库成本案例

首选[时间线首次读取](../apps/server/src/modules/gateway/index.ts)，当前仍读取全群消息并构造完整快照，续页切片已经实现。建议使用隔离库的 1,000 / 10,000 条代表性消息作为两档实验规模；它们是测量输入，不是承诺容量。记录同毫秒、迟到消息等数据分布、索引、统计信息和 PostgreSQL 版本。

执行真实 SQL 的 EXPLAIN (ANALYZE, BUFFERS)，保存计划、扫描/返回行数、buffers、数据库耗时；再测一次实际 API 的响应体量、首屏与续页时延，条件允许时记录进程内存。数据库查询快不等于页面快，不将单次样本冒充 p95 或生产容量。

只在计划和基线证据证明瓶颈后，尝试一个可回滚的索引或局部查询调整，额外上限 1h；验证迟到消息、同毫秒顺序、旧游标、出站确认改时间及快照稳定性。若优化改变快照机制、需大数据回填或结果不稳定，保留测量结论而不改产品。这仍是有价值的交付，不为了展示改动而造优化。

## P1-03：补已有诊断的解释能力

已有管理员诊断 API 和 ModuleProgress 进度。只补最后一次后台失败的稳定类别、已有可靠关联、发生时刻及安全的下一步；无可靠业务实体就展示模块关联，不编造群/消息归因。失败恢复为正常后更新提示，历史记录如实保留。

原始异常、连接串、凭据和消息正文不直接公开。通过受控的真实 tick 失败、后续恢复和 viewer/admin 权限测试验证；未知远端效果的下一步只允许核对已有事实，不出现未经证明的一键重发。

审计阻塞“本次工具未执行”和终态空步骤说明已在首轮修复，不重复开工。审计 reason 的长期存储、完整任务/异常中心、告警平台不包含在本项。PI-04-b、PI-10-b、PI-16-b 的其他流程状态与实际效果解释继续保留在[V2 对应建议](product-enhancement-proposal-v2-20261001.md#effect-status)，不由本项一并覆盖。

<a id="agent-policy"></a>
## P1-04：明确选择后，再加托管目标保护

C2 提示词已限制提议移除自身托管账号，后端当前按原要求检查开关、审计和执行账号权限；提示约束不等于实际派发守卫，也不能由此认定已有实现违反原权限契约。

可选择的新政策为：不自动移除当前群中已确认属于平台托管身份的目标。主后端派发前核对，适用于模拟或真实 Agent；实际目标所属事实变化时不得用过期快照放行。受控模型即使提出请求且审计 pass，受保护目标仍应零远端 kick；普通外部目标保留原流程。

本项已按D050选择，要明确拒绝返回如何兼容现有工具协议，不能自行扩展外部错误码。此次不扩展到额外角色或成员白名单、人工接管、重开积压新规则或模型新工具。新增目标限制的来源和原文差异单列，未改变的其他业务规则保持。

<a id="model-usage"></a>
## P1-05：有界记录真实提供的模型用量

C2 provider 已有 usage observer，正式启动未接持久记录，不能说完全没有用量能力。现有 observer 在成功解析输出后调用，尚未带 run/attempt 标识，因此不只是连接一个保存函数。最小范围为服务内真实可得或明确生成的 request/attempt 标识、turn/audit 用途、模型、耗时、结果，以及供应方实际返回的 usage；缓存复用不能再计为一次新推理，缺失用量记未知，失败不能虚构零消耗。

失败状态需单独记录；未取得可校验的供应方用量时，usage 为未知。已经收到且校验有效的用量，不因后续输出格式或协议校验失败而丢弃；失败不等于没有消耗。服务内标识不能冒充已关联到后端审计步骤。若补齐真实关联与失败记录超出预算，本项退出本轮。采用有界留存，验证写入失败不阻塞业务且可诊断，不写正文与凭据；配置关闭、文件权限及清理范围明确。不做计费、成本承诺或仪表盘，不用现有观测字段推算未报告的 token。优先离线注入合法响应验证，不因本提案新增真实调用。

**2026-10-02 准备期澄清（CONFLICT-USAGE-001）：** 原句“失败状态需单独记录，usage 仍为未知”未区分请求结果与用量是否已知，若据此丢弃有效用量，会与本节“记录供应方实际返回的 usage”目的不一致。本次明确两者分别记录：调用或输出校验失败仍标失败，只有缺失或非法的用量字段为未知，已取得的合法字段可保留。此处修正研发提案表述，不改变工具授权、业务结果或原始要求，不为失败推算用量；历史版本及 QA 已冻结快照保留。具体接入边界见[第二轮交接](second-round-qa-intake-20261002.md#用量结果与已知性)。
